# 目標の評価

## 1. 評価の方法（基準とその理由）

実際の利用者で試せないので、**「目標 → 意図 → 画面の要素 → 証拠」の論証**で評価する。証拠は次の 3 種類だけを使い、自分で確かめたものに限る。

| 証拠 | 中身 | 理由 |
| --- | --- | --- |
| E1 スクリーンショット | `screenshots/*.png`（ブリーフの capture.mjs、1440px／390px、上から 900px）と `screenshots/full/*.png`（補助スクリプトで全体） | 要素が「実際に見える位置にあるか」を確かめる |
| E2 固定データでの数え上げ | `fixtures.ts`（今日 2026-11-09）で、画面に出るべき件数を手で数え、画面と照合 | 「遅れ 1 件・予定の無い週 3 週」など、取りこぼしが無いかを確かめる |
| E3 自動検査 | axe（WCAG 2.1 AA）と横はみ出し（`screenshots/report.json`）、公式 lint、`tsc` | 誰にでも読めること・390px で崩れないことの最低条件 |

各目標は「**最初の画面を開いて、スクロールせずに（1440px）／1 画面分のスクロールで（390px）答えが分かるか**」を基準にする。月曜朝に数十秒で確認する場面（I01）を想定したため。

## 2. 目標ごとの論証

### O1 週 1 本以上を途切れずに公開し続ける

- **意図**：抜けを「無いもの」でなく「空いた枠」として見せ、その場で埋めさせる。
- **画面の要素**：投稿計画（S01）の週の区画。0 本の週は点線の枠＋Lozenge「予定なし」（warning）＋「この週に登録」リンク。上部の SectionMessage に「予定の無い週：3週」と週名。
- **証拠**：
  - E2：既定期間（2026-10-12〜2027-01-03）の今週以降で 0 本の週は、11/23（取りやめの #15 のみ）・12/21・12/28 の 3 週。画面の「予定の無い週：3週 11月23日(月)の週、12月21日(月)の週、12月28日(月)の週」と一致（`screenshots/S01-plan-member-1440.png`、上から約 400px）。
  - E1：390px でも SectionMessage が見出し直下（1 画面目）に入る（`screenshots/S01-plan-member-390.png`）。
  - 「この週に登録」から登録画面を開くと公開予定日にその週の月曜が入る（S35：`/posts/new?date=2026-11-23` の公開予定日欄が「2026/11/23」）。
- **弱いところ**：ペースが続いたか（実績）は、過去の週に「公開なし」を出すだけで、連続週数などの指標は出していない。

### O2 書く人や時期の偏りを減らす

- **意図**：誰が書いていない・誰に集中しているかを表で比べる。時期の偏りは週の本数の並びで見る。
- **画面の要素**：書く人ごと（S15）の表：公開済み・予定・最後の公開・次の予定・予定日超過。予定 0 本の人に Lozenge「予定なし」。投稿計画の週見出しの「N本」。
- **証拠**：
  - E2：既定期間で予定（未公開・取りやめ除く）0 本は、小林 結衣（#13 は日付未定）・中村 彩（#15 取りやめのみ）・加藤 大輔（投稿なし）の 3 人。表の「予定なし」3 件と一致（`screenshots/full/S15-members-member-390.png`）。伊藤 葵は公開済み 2 本で最多。
  - E2：週の本数は 11/2 と 11/9 の週が 2 本、他は 1 本か 0 本（S01）。
- **弱いところ**：偏りの「基準値」（何本以上が偏りか）は示していない。カテゴリの偏りは見られない（要件外として扱った）。

### O3 書く人が自分の担当と予定日を忘れない

- **意図**：開いた瞬間に「次は自分が何をいつまでに」が分かる。
- **画面の要素**：投稿計画上部の「あなたの次の締切は11月12日(木)です」（SectionMessage information）。自分の担当（S09）：これから公開する投稿を予定日の近い順、日付未定は最後。各行の DateLabel に「あと3日」。一覧の書く人名に「（あなた）」。
- **証拠**：
  - E2：id=1 の未公開は #7（11/12・レビュー中）と #14（日付未定）。自分の担当の「これから公開する投稿（2件）」が #7→#14 の順（`screenshots/S09-me-member-1440.png`）。#7 の日付は「11月12日(木)（あと3日）」の warning 表示。
  - E1：S01 の上から約 470px に次の締切。
- **弱いところ**：ブリーフの「Slack 通知」は「デモでは通知を出すだけでよい」に従いログインの通知だけ。締切のリマインド（プッシュ）は無いので、**アプリを開かない人には効かない**。

### O4 取りまとめ役が計画の抜けや遅れに早く気づける

- **意図**：一覧を読まなくても、最初の画面の最上部で「何件・どれ」が分かる。
- **画面の要素**：投稿計画上部の SectionMessage(warning)「計画に遅れと抜けがあります／予定日を過ぎた投稿：1件（テストの書き方ガイドライン（仮）・11月5日・執筆中）」。週の一覧の DateLabel danger「11月5日(木)（4日超過）」。書く人ごとの「予定日超過」列。
- **証拠**：
  - E2：今日 11/9 で予定日を過ぎた未公開は #6 の 1 件だけ。画面の 1 件と一致（S01・S03）。近い（7 日以内）は #7（11/12）と #8（11/13）で、どちらも warning 表示。
  - E3：DateLabel はアイコン＋文字（「超過」「あと N 日」）を持ち、色だけに頼らない。axe 違反 0（下記）。
- **弱いところ**：気づいた後の「誰に頼むか」は書く人ごとの表に移る必要がある（同じ画面にない）。

## 3. 自動検査の結果（E3）

- capture.mjs（46 状態 × 2 幅 = 92 枚）：結果は `screenshots/report.json`。1 回目は 1440px のログイン中の全状態で `aria-required-children(1)`（TopNavEnd の `role="list"` に Button を直接置いた）→ `li` で包んで修正。2 回目の結果は下の「最終結果」。
- 横はみ出し：1 回目から全状態 0。
- 公式 lint：0 errors / 0 warnings。`tsc -b`：エラー 0。

**最終結果（2 回目）：92 件すべて axe 違反 0・横はみ出し 0**（`screenshots/report.json`）。1 回目の結果は修正前の記録として本文に残した。

## 4. 評価の限界

- 利用者による検証をしていない。論証は「要素がある・見える・数が合う」までで、「実際に早く気づくか」「忘れなくなるか」は測っていない。
- 固定データ 15 件・メンバー 10 人だけで確かめた。投稿が 100 件・1 週 5 本などになったときの一覧の長さや、書く人ごとの表の読みやすさは未確認。
- 390px の書く人ごとの表は 6 列を押し込んでおり、横はみ出しは 0 だが、見出しが 2〜3 行に折り返す（`screenshots/full/S15-members-member-390.png`）。読めるが快適ではない。
- capture.mjs のスクリーンショットは ADS Layout の内部スクロールのため上から 900px しか写らない。全体は補助スクリプトの画像で確認した（検査結果は capture.mjs のものを正とする）。
- 保存は画面内の状態だけで、再読み込みで固定データに戻る（ブリーフどおり）。保存・削除の失敗は `?fail=save|delete` と `?flag=` で再現したもので、実際の通信エラーではない。
- axe は自動で検出できる範囲だけ。キーボードでの一連の操作とスクリーンリーダーでの読み上げは、ダイアログの開閉と Flag の表示を除き確かめていない。
