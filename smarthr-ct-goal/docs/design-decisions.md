# 設計判断（design-decisions）

> 状態：§0〜§8 は**実装前に書いた下書き**（コミット `63b6948`）をほぼそのまま残し、実装で変わった点は §9「実装後の追記」にまとめた。
> 出典の書き方：`[H:ファイル名]` ＝ SmartHR Design System のハーネス（プラグインのスキル）、
> `[D:ファイル名]` ＝ ハーネス外の SmartHR 公式ドキュメント（同リポジトリの記事）、
> `[自]` ＝ 自分の判断（事前知識・ブリーフの読み取り）。

## 0. 主役の決め方

ブリーフの主な利用シーンは「月曜の CT 前に今週の相手を確かめ、そのままハドルを始める。滞在は数十秒」。
そこで **組み合わせ画面の最上部に「今週のあなたの相手」と「ハドルを始める」（画面で唯一の Primary ボタン）を置く**ことを主役とする。

- 「重要な情報は上部・左側に」「優先度が高い情報は上部に」 `[H:visual-guidance.mdx]`
- 「Primary ボタンは 1 画面に最大 1 つ。主要な操作が 1 つになるよう情報設計を見直す」 `[H:components/Button.md]`
  → Primary をどこに使うかを決めることが、そのまま「主役は何か」を決めることになった。
- ただし「今週の自分の相手を最上部に別枠で出す」という**発想そのものはハーネスに無く**、ブリーフ（G1/G2）からの自分の判断 `[自]`。
  ハーネスのページレイアウトは「コレクション」「シングル」という**業務オブジェクト中心の型**で、「ある人にとっての今日の答え」を主役にする型は無い。

## 1. 目標 G1〜G7 をどこで達成するか（下書き）

| 目標 | 画面・要素 | 根拠 |
| --- | --- | --- |
| G1 今週の相手がすぐわかる | 組み合わせ画面の見出し直下のセクション「今週のあなたの相手」。相手のアイコン・名前を大きめに表示し、日付と「14:00 開始」を添える。390px でも最初の画面内に収める | 上部配置 `[H:visual-guidance]`、別枠化は `[自]` |

| G3 先の週の予定 | (a) 同セクション内に「あなたの今後の予定」（DefinitionList：来週以降の相手／お休み／CT なし）、(b) セクション「週ごとの組み合わせ」で TabBar により週を切り替え、各週に「予定」StatusLabel | 長いページを避けナビゲーションで分割 `[H:page-layout]`、TabBar で Panel 切替 `[H:visual-grouping]` |

## 2. 画面構成（下書き）

すべての画面：AppHeader（ロゴ＝Gaji-Labo、アプリ名「CTスケジュール」、ナビ「組み合わせ」「メンバー」「自分の設定」、ログイン中は名前とアイコン、未ログインは「Slack でログイン」）→ Container → PageHeading＋リード文 → セクション `[H:page-layout]`

1. **組み合わせ**（`/`）— 「シングル（1 カラム）」の型を借りる。セクションは
   1. 今週のあなたの相手（ログイン中）／ログインすると何ができるか（未ログイン）
   2. 週ごとの組み合わせ（TabBar：今週・来週・以降の予定。各週はペアのリスト＋お休みの人＋参加者数とメンバー画面へのリンク）
2. **メンバー**（`/members`）— 「コレクション（テーブル）」、モバイルは「コレクション（リスト）」
3. **自分の設定／初回設定**（`/settings`）— フォーム 1 画面
4. **存在しないページ** — ErrorScreen

## 3. 決まっていないことの決め方（下書き）

| 項目 | 決めたこと | 理由 |
| --- | --- | --- |
| どちらの uチャンネルでハドルするか | **ペアのうち社員番号が後の人の uチャンネル**。ボタンの近くにチャンネル名を明記 | 2 人が別々のチャンネルに行かないよう 1 つに決める必要がある。ブリーフの S09（id=2 の uチャンネル未設定→今週の id=1 のペアでボタンを出さない）とも矛盾しない。ログイン中の id=1 から見ると常に「相手の」チャンネルになる `[自]` |
| メンバー削除を全員に許すか | ログイン中の全員に許す。ただし自分自身は削除できない（行に削除ボタンを出さない） | ブリーフの機能要件「ログイン中の人はメンバーを削除できる」に従う。自分を消すと操作中の画面が壊れるため `[自]` |
| 先の週をどこまで見せるか | 固定データの 5 週すべて（今週＋4 週）。今週以外には「予定」ラベル | データがある範囲。「予定」はルール 7 `[自]` |
| スマートフォンをどこまで想定するか | 組み合わせ画面と設定画面はモバイルでも同じ操作ができる。メンバー画面はリストに切り替え、削除もできる | モバイル利用が多い前提 `[H:mobile-friendly-layout]`。Slack の通知からスマホで開く人が多いはず `[自]` |
| 「特定の人と次に当たるのはいつか」 | 入れない | 主目的（数十秒の確認）から外れ、画面が長くなる `[H:page-layout]「ページが過度に長くなることを避ける」`、`[自]` |
| 参加者数の数え方 | 「参加者 9 人」を主に、メンバー画面では「参加 9 人・不参加 2 人（全 11 人）」 | 組み合わせに関係するのは参加者だけ（ルール 5）`[自]` |
| 社員番号 | 固定データに社員番号が無いので id を社員番号として扱う | 並び順（ルール 6）が id 順と一致する `[自]` |

## 4. 通知の使い分け（下書き）

| 場面 | 部品 | 出典 |
| --- | --- | --- |
| ハドル開始（デモ） | ボタン直下の ResponseMessage(info) | `[H:feedback]` 操作部の近く |
| Slack ログイン（デモ） | ヘッダー直下の NotificationBar(info) | 画面全体に関わる操作 `[H:feedback]` |
| Slack ログイン失敗 | ヘッダー直下の NotificationBar(error, bold)＋「もう一度ログインする」 | `[H:feedback]`。AuthErrorScreen は採らない（下記） |
| 組み合わせの読み込み中 | セクションの位置に Loader | `[H:feedback]` |
| 組み合わせの読み込み失敗 | セクションの位置に NotificationBar(error, bold)＋「再読み込み」 | `[H:feedback]`「特定の要素の表示に失敗した場合」 |
| 設定の保存成功／失敗／未入力 | 保存ボタンの近くに ResponseMessage(success/error)、未入力は FormControl の errorMessages も | `[H:feedback]`、`[H:FormControl]` |
| メンバー削除の確認・失敗 | ActionDialog（失敗は responseStatus=error） | `[H:delete-dialog]`、`[H:feedback]` |
| メンバー削除の成功 | ダイアログが閉じて画面が切り替わるので NotificationBar(success, bold) | `[H:feedback]`「Button の近くに表示するのが難しい場合」 |

**AuthErrorScreen を採らない理由**：component-selector は「SSO や OAuth などログイン処理に失敗したときに使います」とするが、実物（v102.1.0）は文言が「認証で問題が発生しました」「SmartHR に戻る」で固定され、やり直し（もう一度ログイン）の導線を置けない。さらに全画面になり、未ログインでも見られるはずの組み合わせが見えなくなる。G7（次に何をすればよいか）を優先した `[自]`。

## 5. 色の意味（下書き）

- 色はすべて smarthr-ui のトークンを使う（背景 BACKGROUND、Panel は WHITE、操作は MAIN、エラー DANGER）。
- 参加／不参加は StatusLabel（参加＝`blue`、不参加＝`grey`）＋**文字**で区別する（色だけに頼らない）`[H:StatusLabel]`。
- 「予定」「CT なし」も StatusLabel（`grey`）。
- 人のアイコン色（`fixtures.ts` の color）はトークンに無い色（purple）を含むため、**自前 CSS が必要**（§7）。

## 6. 文言（下書き）

- 画面タイトル・見出しは名詞（「組み合わせ」「メンバー」「自分の設定」）、ボタンは動詞の終止形（「ハドルを始める」「保存」「削除」）`[H:Heading][H:Button]`、`[D:ui-text/app-writing]`
- 見出しに「一覧」をつけない `[H:smarthr-list]`
- エラーは事象・原因・対処 `[D:error-messages/overview]`
- 削除ダイアログは定型文 `[H:delete-dialog]`

## 7. 自前 CSS（予定）

- 人のアイコン（頭文字＋固定色の円）。smarthr-ui にアバター部品が無い（component-selector の 100 余件に無い）ため。

## 8. 妥協点（下書き）

- AppHeader のロゴリンクは `target` を指定できない（LogoLink が `<a href>` 固定）。ブリーフの「別タブで開く」を満たすため、ロゴ要素に別タブを開く処理を足す必要がある。
- NotFoundErrorScreen はロゴが SmartHR 固定。Gaji-Labo のサービスなので ErrorScreen（logo を渡せる）で組み立てる。

## 9. 実装後の追記（下書きから変わった点・決めた点）

### 9.1 画面ごとの最終的な構成

| 画面 | 構成 | 主な判断 |
| --- | --- | --- |
| 共通 | Header（Gaji-Labo ロゴ、右端にログイン中の人のアイコン＋名前のメニュー〔自分の設定を変更／ログアウト〕、未ログインは「Slackでログイン」）＋AppNavi（「CTスケジュール」ラベル、組み合わせ／メンバー／自分の設定）＋ヘッダー直下の通知 | **AppHeader をやめて Header＋AppNavi にした**。AppHeader は「個人設定」が別タブ固定、モバイルのメニューに「アプリ一覧」「リリースノート」「管理メニュー」など SmartHR 固有の項目が出るため。Header.md の「独自のヘッダー構成が必要なときのみ Header 単体」に当たると判断 `[H:Header.md]` `[自]` |
| 組み合わせ `/` | PageHeading「CTの組み合わせ」＋リード文（14:00 開始・11:00 に Slack へ投稿）→ セクション「今週のあなたの相手」（日付、相手を大きく、Primary「ハドルを始める」と場所、「あなたの今後の予定」）→ セクション「週ごとの組み合わせ」（参加者数とメンバーへのリンク、TabBar「今週／来週／10月19日…」、週ごとの Panel） | 未ログインでは 1 つ目のセクションの代わりに InformationPanel「ログインすると、あなたの相手がすぐにわかります」と Primary「Slackでログイン」 |
| メンバー `/members` | PageHeading「メンバー」＋リード文 → セクション「参加状況」（参加・不参加・全体の人数、デスクトップはテーブル〔社員番号・名前・参加状況・uチャンネル・操作〕、モバイルはリスト） | 自分の行には削除の代わりに「設定を変更」。未ログインでは操作列を出さず「ログインすると削除できる」と添える |
| 自分の設定 `/settings` | PageHeading「自分の設定」（初回は「初回設定」）＋リード文 → Panel 内のフォーム（名前、社員番号、uチャンネル、CTへの参加）→ 保存とその結果 | 初回設定が済んでいない人は、組み合わせ・メンバーを開いても初回設定へ移す |
| 存在しないページ | ErrorScreen（Gaji-Labo ロゴ、見出し、説明、「組み合わせに戻る」） | |

### 9.2 主役を目立たせる手段

- 相手の名前は Text `XL`・bold、アイコンは 3rem にし、周りの文字より一段大きくした。見出しではなく「答え」なので Heading にはしていない。
- Primary ボタンは画面で 1 つ。週ごとのリストのハドルボタンは Secondary。
- モバイルでは Primary を幅いっぱいにした `[H:Button.md]`。

### 9.3 文言（実装後）

- textlint で「全角と半角の間にスペースを入れない」に合わせ、「Slack でログイン」→「Slackでログイン」、「CT の組み合わせ」→「CTの組み合わせ」、「2 人 1 組」→「2人1組」などに直した `[L:textlint-rule-preset-smarthr]` `[D:idiomatic-usage/symbol]`。
- エラー文は「事象。原因・対処。」の順：「保存できませんでした。通信状況を確認して、もう一度「保存」を押してください。」`[D:error-messages/overview]`
- 削除ダイアログ本文は定型どおり「以下のメンバーを削除しますか？　この操作は元に戻せません。」（「？」の後に全角スペース）`[H:delete-dialog]`
- 敬称：相手の名前は「さん」をつけず表示（一覧・メンバーと揃える）。文中で人を指すときは「〇〇さん」。

### 9.4 自前 CSS（最終）

| ファイル | 内容 | 理由 |
| --- | --- | --- |
| `src/components/person.css` | 人のアイコン（円、頭文字、4 色） | smarthr-ui にアバター部品が無い。purple がトークンに無い。白文字・黒文字はコントラスト 4.5:1 以上になる組み合わせ（blue 4.75、green 4.77、orange は黒文字で約 5.0） |
| `src/components/logo.css` | Gaji-Labo ロゴ（SVG）の大きさと色 | ロゴは smarthr-ui の部品ではない |

ほかにクラス名として `shr-*`（smarthr-ui が配布するユーティリティクラス：`shr-list-none`、`shr-ps-0`、`shr-m-0`、`shr-p-1`、`shr-border-t-shorthand`、`shr-sticky` など）を使った。これはトークンに基づくクラスなので自前 CSS には数えていない。

### 9.5 妥協点（最終）

1. **ロゴの別タブ**：Header のロゴリンクは `target` を受け取らないので、描画後に `a.smarthr-ui-Header-logoLink` に `target="_blank"` と `rel` を付けている（`Layout.tsx`）。ロゴの代替テキストに「新しいタブで開きます」を入れた。
2. **ヘッダーの名前の文字色**：Header の背景（BRAND）に白文字だと 2.14:1 で AA 未達のため、名前に `TEXT_BLACK` を明示した。アイコン・ロゴは白のまま。
3. **ログイン失敗**：AuthErrorScreen（推奨部品）を使わず NotificationBar にした（§4）。
4. **組み直しのデモ**：参加をやめる・メンバーを削除しても、固定データの組み合わせは変わらない（ルールどおり計算はしない）。画面上は「組み直しました」と伝えるだけ。
5. **社員番号**：固定データに無いので id を 4 桁で表示（0001〜0011）。
6. **週ごとのハドルボタン**：全ペアに出す（ブリーフの要件）ため、ボタンが 4 つ並ぶ。主役のボタンだけ Primary にして差をつけた。
7. **ブランド**：Header の背景は SmartHR のブランド色（BRAND）のまま。Gaji-Labo の色に変えるにはテーマの上書きが要り、「smarthr-ui のトークン・テーマを使う」という条件を優先した。
