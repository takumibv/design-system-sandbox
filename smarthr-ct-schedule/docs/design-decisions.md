# SmartHR Design System 版のデザイン判断

原本（DADS 版）の判断は [digital-go-design-system `docs/design-decisions.md`](https://github.com/takumibv/digital-go-design-system/blob/codex/ct-schedule-ui/docs/design-decisions.md)、ADS 版の判断は [ads-ct-schedule/docs/design-decisions.md](../../ads-ct-schedule/docs/design-decisions.md) にあります。ここでは SmartHR Design System で作り直したときに、何を引き継ぎ、何を変えたか、その理由を記録します。

判断の多くは SmartHR の公式スキル（`component-guidelines`／`design-pattern-guidelines`）から来ています。どの判断がどこから来たかの一覧は [harness-report.md](harness-report.md) にまとめました。

## 基本方針

ADS 版と同じ 3 つの方針にしました。

1. **中身は原本と同じにする。** 画面構成、読む順序、16 の状態、固定データは変えていません。文言も原本のままです。SmartHR のライティング規則とぶつかった箇所も、原本の文言を残して衝突として記録しました（[harness-report.md](harness-report.md) の「日本語 UI 規約との衝突」）。例外はパンくずだけです。SmartHR にはパンくずの部品がないため、UpwardLink に置き換え、文言も規則どおり「CT組み合わせ表に戻る」にしました。
2. **見た目は SmartHR の標準に任せ、寄せるための上書きをしない。** 自前の CSS ファイルは書いていません（`src/index.css` は Tailwind のユーティリティを生成する 1 行だけ）。色・余白・角丸・影は、smarthr-ui が配布する Tailwind プリセット（`shr-*`）のトークンだけを使っています。
3. **迷ったら ADS 版と原本の判断に合わせる。** ただし SmartHR のチェックリストに `[must]` がある場合は、それを優先しました。

## 利用者と主役

主な利用者は、原本・ADS 版と同じく「月曜の CT 直前に相手を確認するメンバー」です。いちばん知りたいのは「今週の自分の相手は誰で、どこで話せばよいか」です。

- **「今週のあなたのCT」を主役にした。** 白い Panel に、大きなアバター 2 つと Primary ボタンを中央に置きました。ページの背景は SmartHR の標準どおり薄いグレー（`BACKGROUND`）にしています。白い Panel が背景から浮くので、ADS 版のように色付きの面を使わなくても主役が分かります。
- **Primary ボタンは画面に 1 つ**にしました。それが「Slack でハドルを始める」です。これは Button のチェックリスト `[must] 1 つの画面で Primary ボタンは最大 1 つまでにする` に従った結果で、原本・ADS 版の判断とも一致します。一覧のハドルボタンは Secondary・小サイズです。
- 原本の濃い青の上ボーダーは再現していません。SmartHR の「視覚的グルーピング」は「矩形（Panel）と余白でまとまりを示し、罫線は最終手段」としているためです。

## 画面ごとの判断

### 共通（ヘッダー・ページの骨組み）

- ページの構成は、デザインパターン「ページレイアウト」の「ヘッダー → コンテナ領域（見出し領域 → コンテンツ領域）」に合わせました。本文は `Container`（DEFAULT）、画面タイトルは `PageHeading`、その下にリード文を置いています。
- ヘッダーは 2 段です。上段は `Header`（ロゴと「Communication Time」）、下段は `AppNavi`（「CT組み合わせ表」「メンバー一覧」の切り替えと、ログイン中の名前・ログアウト）。SmartHR の推奨は `AppHeader` ですが、SmartHR のテナント切り替えやヘルプ導線など SmartHR 製品専用の機能が中心のため使いませんでした。
- `AppNavi` はモバイル用の表示を持たず、390px で横にはみ出しました。モバイルではラベルとアカウント操作を外し、アカウント操作は `AppNavi` の下に別の行として出しています。
- 原本のパンくずは `UpwardLink`（「CT組み合わせ表に戻る」）にしました。チェックリストどおり、モバイルとサイドナビなしの画面では `indent` を無効にしています。
- 余白は「余白の取り方」の表に合わせました。見出し領域とコンテンツの間は 1.5（24px）、セクション同士は 2（32px）、見出しとコンテンツの間は 1（16px）です。

### CT組み合わせ表

- **レイアウト**：PC は「本文＋右の補足欄」の 2 カラムで、`Sidebar` を使っています。パターン「シングル（2 カラム）」の「主情報の幅は副情報の 2 倍以上」に合わせ、補足欄の基準幅を 20rem にしました。幅が足りなくなると自動で縦に積まれます（「モバイルでは複数カラムを避ける」）。
- **週の移動**：前後の矢印は、アイコンだけのボタンにして `alt`（「前の週」「次の週」）を付けました（`[must]` アイコンボタンには alt を設定する）。今週を表示しているときは「前の週」と「今週」を押せなくしていますが、`[avoid]` 無効状態のボタンはできるだけ使わない、に従い `disabledReason` で理由を出しています。見た目には ⓘ アイコンが増えます。
- **週のラベル**：「今週／来週／予定」は週の状態なので `StatusLabel` にしました。今週は青の強調、それ以外はグレーです。
- **みんなの組み合わせ**：1 ペアを 1 行のリストにして Panel に入れました。自分のペアの行は、メインカラーを 10% 透過した背景にしています。「あなた」は状態ではなく属性なので、StatusLabel ではなく `Chip` にしました（Chip の `[must]` ステータス表示には Chip を使わない、の裏返し）。
- **この先の CT**：ADS 版と同じく縦のリストにし、行全体を Text ボタン（右に › アイコン）にしました。`[must]` Text ボタンを単独で使うときはアイコンを付ける、に従っています。祝日の週は警告色の `StatusLabel`「祝日のためお休み」です。
- **補足欄**：「CTに参加する人」は Panel、「CTの過ごし方」は Panel なしにしました。矩形を増やしすぎない（「矩形の過度な使用は画面を冗長にする」）ためです。
- **画面遷移はリンクにした**：「メンバー一覧を見る」「自分の参加設定を変更する」は `TextLink` です。ADS 版では後者を subtle ボタンにしていましたが、SmartHR の `[must]` 他の画面へ移動するなら TextLink、に従いました。目立たせたい遷移（「自分の設定を開く」「CT組み合わせ表へ戻る」）は `AnchorButton` です。

### メンバー一覧

- 上部に「参加する／参加しない」の人数を Panel で並べ、全体の状況を先に伝えます。
- PC は `Table`（よくあるテーブル）です。操作は右端の列に置きました（「オブジェクトの操作は右端」「1 行のボタンは 3 つまで」）。
- **モバイルでは表をリストに切り替えました**。パターン「よくあるテーブル」の「モバイルではよくあるリストを使う」に従っています。判定にはパターンの指示どおり `useEnvironment` を使いました。結果として、原本のモバイル表示（カード型のリスト）とほぼ同じ構造になりました。
- 「削除」は Secondary を 11 個並べると重くなるため、ゴミ箱アイコン付きの Text ボタンにしました（`[should]` Secondary が多い場合は見直す、`[must]` Text ボタン単独ならアイコン）。
- 「初回設定が未完了」は、ADS 版ではラベル（Lozenge）でした。SmartHR では `[avoid]` 1 つのオブジェクトに複数の StatusLabel を付けない、があるため、参加状況だけを StatusLabel にし、未完了は警告アイコン付きの文字にしました。
- メンバーが 0 人の状態は、パターン「よくあるテーブル／初期表示」どおり、Panel の中にメッセージと Secondary・小サイズのボタンを中央に置きました。ADS 版ではここのボタンが primary でした。

### 削除の確認

- `ActionDialog`（開閉をアプリ側で持つので `ControlledActionDialog`）の S サイズにしました。実行ボタンは Danger、キャンセルは左です（パターン「削除ダイアログ」）。
- タイトル・本文・ボタンの文言は原本のままにしました。パターンは「タイトルは `{オブジェクト名}の削除`」「本文は `以下の{オブジェクト名}を削除しますか？　この操作は元に戻せません。`」「削除対象を DefinitionList で示す」「ボタンは `削除`」としていますが、文言を原本と揃える方針を優先しました。
- 削除に失敗した状態は、ダイアログの `responseStatus`（ボタンの横にエラーを表示）で出しています。パターン「フィードバック」の「ActionDialog の場合は responseStatus」に従いました。
- 最初のフォーカスは smarthr-ui の既定（ダイアログ本体）のままです。原本・ADS 版は「キャンセル」に置いていましたが、`closeButton` は ref を受け取れないため指定できませんでした。

### 自分の設定・初回設定

- 各項目は `FormControl` で、ラベルの横に `RequiredLabel`（必須）、その下にヘルプ文、エラー時はエラー文を出します。原本のヘルプ文の位置（ラベルの直下）は、SmartHR の FormControl の標準と同じでした。
- 入力欄は Panel の中にまとめ、送信ボタンは Panel の外の下に置きました（パターン「フィードバック」の実装例と同じ配置）。
- **エラーは 2 段構え**：上部の `InformationPanel`（error）で「何を直せばよいか」をまとめ、各項目に `errorMessages` を出します。エラーは入力を直すとその場で消えます（`[must]` 原因が解消されたら表示を止める）。送信時は最初のエラー項目にフォーカスを移します。
- 保存に失敗した状態は、保存ボタンの横の `ResponseMessage`（error）にしました。ADS 版では上部の SectionMessage でした。「操作部の近くでフィードバックする」に従った変更です。
- 参加の切り替えは原本と同じ Checkbox を `Fieldset` で囲みました。`[must]` Fieldset は 2 つ以上の入力要素に使う、には反します。ただし Checkbox を FormControl に入れることは lint（`a11y-input-in-form-control`）で禁止されており、ほかに legend を付ける手段がないため、こちらを選びました。
- 保存は Primary、キャンセルは Secondary です。PC では横並び（Primary が右）、モバイルでは保存ボタンを幅いっぱいにしています。

### 読み込み中・失敗・404

- 読み込み中は `Loader`、失敗は Panel の中に見出し・説明・「再読み込み」ボタンです。
- 404 は `NotFoundErrorScreen` を検討しましたが、ヘッダーを含めた全画面の部品なので、原本と同じく「ヘッダーの下に 404 を出す」形にはできません。Panel と AnchorButton で組みました。

## 通知の使い分け

パターン「フィードバック」の基準に合わせて、3 種類に分けました。ADS 版（SectionMessage と Flag の 2 種類）より細かくなっています。

| 種類 | 部品 | 例 | 理由（パターンの記述） |
| --- | --- | --- | --- |
| 操作したボタンのすぐ横 | `ResponseMessage` | ハドルのデモ通知、Slack ログインのデモ通知、保存失敗、削除失敗（ダイアログの `responseStatus`） | 「直前に操作していた要素の近くにフィードバックする」。拡大鏡を使う人は離れた場所の変化に気づけない |
| 画面全体の操作結果 | `NotificationBar`（bold、animate、sticky、閉じるボタンあり） | 保存しました、削除しました、ヘッダーのログインのデモ通知 | 「画面全体が切り替わるなどボタンの近くに出せないときは NotificationBar[bold]」「時間で自動的に閉じない」 |
| 続いている状態 | `InformationPanel`／`NotificationBar`（paneled）／`NotificationBar`（error） | 未ログインの案内、入力エラーのまとめ／不参加中／ログイン失敗 | 「複数行や見出しが必要なら InformationPanel」「一文で済むなら paneled の NotificationBar」 |

ADS 版では成功通知を画面隅の Flag（自動で消える）にしていました。SmartHR には Flag に当たる部品がなく、NotificationBar の `[avoid]` 時間の経過で閉じない、により、自分で閉じるまで残ります。

## 色の意味

色は SmartHR のトークンだけを使いました。どのラベルも文字で意味が読めるので、色が分からなくても困りません（`[must]` 色のみでステータスを伝えない）。

| 色 | 使った場所 | 意味 |
| --- | --- | --- |
| 青（`StatusLabel` blue bold、`Chip` blue、メインカラー 10% の背景） | 今週、あなた、自分のペアの行 | 自分や現在に関係する |
| 緑（`StatusLabel` green） | 参加する | 良い状態 |
| グレー（`StatusLabel` grey） | 参加しない、来週・予定、今週のお休み | 中立 |
| 黄（`StatusLabel` warning、`WarningIcon`） | 祝日のためお休み、初回設定が未完了 | 注意してほしい |
| アバターの背景（メイン・グリーン・警告黄・デンジャーの 15〜30% 透過） | 人の頭文字 | 人を見分ける。原本の 4 色（青・緑・紫・橙）に近いトークンを当てた。紫と橙のトークンはないので、デンジャー（ピンク寄り）と警告黄で代用 |

## アクセシビリティ

- 見出しは `PageHeading`（h1）と、`Section`／`Aside` の中の `Heading` で組みました。見出しレベルは smarthr-ui が自動で計算します。lint（`a11y-heading-in-sectioning-content`）が、Section の外に置いた Heading を 4 か所見つけてくれました。
- 「本文へ移動」のスキップリンクは smarthr-ui にないため、Tailwind の `sr-only` で作りました。
- 画面を切り替えたら本文（`main`）にフォーカスを戻します。lint は `main` の tabIndex を禁止していますが、SPA のフォーカス管理に必要なので、理由を書いて 1 か所だけ抑止しました。
- axe（WCAG 2.1 AA）は 16 状態 × 2 幅の 32 ケースすべてで違反 0 件、横はみ出しも 0 件です。

## 再現できなかったこと（妥協点）

| 原本の意図 | SmartHR 版でどうなったか | 理由 |
| --- | --- | --- |
| 色付きのイニシャルで人を見分ける | 自作のアバター（トークン色の透過＋頭文字）で再現 | smarthr-ui に Avatar がない。ADS 版（人型アイコンのみ）よりは原本に近い |
| パンくず | 「CT組み合わせ表に戻る」の UpwardLink | Breadcrumb がない。文言も変わった |
| ゆったりした余白と大きな文字（見出し 32px 太字） | 本文は原本と同じ 16px。画面タイトルは 24px・標準の太さ。ページの縦の長さは原本より約 2〜3 割短い | SmartHR の業務アプリ向けの密度。長さは ADS 版とほぼ同じ |
| 濃い青の強いアクセント・太い上ボーダー | 白い Panel ＋ Primary ボタンで主役を示す | 罫線は「最終手段」。メインカラーも DADS の濃紺より明るい青 |
| Noto Sans JP で統一 | `system-ui, sans-serif` になり、和文は OS 依存 | smarthr-ui の CSS は和文フォントを指定していない（実測。ADS と同じ） |
| 削除確認の最初のフォーカスを「キャンセル」に | ダイアログ本体にフォーカス | `ControlledActionDialog` の `closeButton` に ref を渡せない |
| 成功通知が自然に消える（ADS 版） | 閉じるまで残る | SmartHR は「時間で閉じない」 |

## まとめ

**「何を主役にし、どの順に読ませるか」は、SmartHR でもそのまま実現できました。** ADS 版と違うのは、判断の根拠をスキルのチェックリストとパターンから引けたことです。通知を「ボタンの横／画面全体／続く状態」の 3 つに分けたこと、画面遷移を TextLink にしたこと、モバイルでテーブルをリストに替えたことは、どれもスキルを読んで決めました。一方で、文言の規則（ボタンは動詞の終止形、削除ダイアログの定型文など）は原本とあちこちでぶつかり、今回は原本を優先しています。SmartHR 版は「SmartHR の業務画面の一部」のような、落ち着いた見た目になります。
