# 目標の自己評価

評価記号：◎＝十分に達成、○＝達成（小さな課題あり）、△＝一部のみ、×＝未達成。
スクリーンショットは `screenshots/<状態ID>-<幅>.png`（幅は 1440 と 390、ビューポートの高さ 900px、ページ全体を撮影）。

## 1. 評価の方法

### 基準をどう決めたか

ブリーフの目標は、どれも「**誰が・どの瞬間に・何がわかる／できるか**」で書かれています（例：G1「月曜の CT 直前、Slack から来た人が、開いてすぐ今週の相手がわかる」）。そこで、見た目の好みではなく、**その瞬間の利用者が目的を果たすまでの「手数」と「迷う余地」**で測ることにしました。具体的には、目標ごとに次の 5 つの観点のうち当てはまるものを使います。

| 観点 | 何を見るか | この観点を選んだ理由 |
| --- | --- | --- |
| A. 手数 | 目的を果たすまでのクリック回数とスクロール量（Playwright で計測） | G1・G2 は「すぐ」が要件。「すぐ」を数値にできるのは操作回数とスクロール量 |
| B. 最初の画面 | 高さ 900px のビューポートに、目的に必要な要素（相手の名前・ハドルのボタンなど）が入っているか。要素の上下の位置（px） | 滞在が数十秒のアプリでは、スクロールしないと見えない情報は「無い」のと近い |
| C. 状態ごとの文言 | その状態で「何が起きているか」と「次に何をするか」の 2 つが文として画面にあるか | G7 の定義そのもの。どの状態でも、利用者が次の一手を自分で推測しなくて済むかを見る |
| D. ハーネスとの照合 | 部品の選び方・通知の使い分け・primary の数が、Ant Design の DESIGN.md・spec・whenToUse に沿っているか | 「Ant Design で作る」こと自体が条件。慣れたパターンに沿うと、利用者が迷いにくい（DESIGN.md の価値「Natural」「Certain」） |
| E. 機械検査 | axe（WCAG 2.1 AA）の違反数、横はみ出し（px）、`antd lint` の件数、操作の通り道のテスト | 色だけに頼らない区別、390px での利用など、ブリーフが明示する条件を客観的に確かめるため |

評価記号の付け方：その目標の「瞬間」で、観点 A・B（手数・最初の画面）と C（文言）を満たし、E で違反が無ければ ◎。目的は果たせるが、スクロール・追加の操作が要る、またはデモの制約で一部を文でしか伝えられない場合は ○。

## 3. 目標ごとの論証

各目標を「目標 → 設計の意図 → 画面のどの要素か → 確認した証拠」の順に書きます。

### G1 開いてすぐ今週の相手がわかる ◎

- **目標の瞬間**：月曜の CT 直前、Slack の投稿やブックマークから開いた人。滞在は数十秒。
- **設計の意図**：
  1. この瞬間に要る情報は「相手は誰か」だけ。全ペアの一覧から自分を探させない（ブリーフ「探さずにわかる」）。
  2. そのため、自分の相手だけを抜き出した 1 枚のカードを**ページ見出しの直下**に置き、相手の名前を見出し（h2）にする。ページで最も大きい文字はページ見出し（24px）と相手の名前（20px）だけにする。
  3. 「いつ話すか」も同じカードで答える（右上に「10月5日（月） 14:00〜」）。
  4. 相手がいない週（お休み・祝日・参加者 2 人未満）でも**同じ場所**に理由と次の予定を出し、利用者が見る位置を変えない。
- **画面の要素**：ホームの主役カード「今週のあなたの相手」。アバター（64px、390px では 48px）、名前（h2）、日付と開始時刻。
- **証拠**：
  - 手数（A）：両方の幅で操作 0 回・スクロール 0 で名前が見える。名前の下端は 1440px で 277px、390px で 298px（`docs/g1g2-measure.json`）。
  - 最初の画面（B）：S01-1440・S01-390 で、名前は高さ 900px の上 3 分の 1 に入っている。
  - 相手がいない週（C）：S03（「今週はお休みです」「参加者が奇数のため」「次は 10月19日（月） 14:00〜、小林 結衣さん」）、S04（「今週は CT がありません」＋スポーツの日の Tag＋次の相手）、S05（「今週の相手はいません」「2 人未満のため」）。
  - 未ログイン（S02）：同じカードが「ログインすると、今週の相手がここに表示され、そのままハドルを始められます」になる。
- **◎ とした理由**：観点 A・B・C をすべて満たし、相手がいない週にも見る場所が変わらない。

### G2 その相手との通話をすぐ始められる ◎

- **目標の瞬間**：G1 と同じ。相手を確かめたら、そのまま通話に入りたい。
- **設計の意図**：
  1. 確かめる（G1）と始める（G2）を**同じカードの中で上から下へ**続ける。視線を動かさずに押せる位置にボタンを置く。
  2. ボタンを**画面で唯一の primary** にする（DESIGN.md・spec buttons「primary は最重要の 1 操作だけ」）。全ペアの一覧にある「ハドル」は text ボタンにして、主役と競わせない。
  3. ボタンの文言に相手の名前を入れ（「高橋 健太さんとハドルを始める」）、押すと何が起きるかを予測できるようにする（spec buttons「ラベルは結果を表す動詞」）。
  4. 2 人が別々の場所で待たないよう、**ハドルの場所をペアで 1 つに決めて**ボタンの上に出す（「ハドルの場所：#u-kenta（2 人で共通）」）。
  5. 相手の uチャンネルが未設定なら、押せないボタンを置くのではなく、理由と代わりの手段を文で出す。
  6. 390px ではボタンを横幅いっぱいにして、親指で押しやすくする。
- **画面の要素**：主役カードの primary ボタンとハドルの場所の表示。S09 では warning の Alert。
- **証拠**：
  - 手数（A）：ログイン中はクリック 1 回。未ログインで開いた場合はクリック計 2 回（ログイン → ハドル）。どちらもスクロール 0（`docs/g1g2-measure.json`）。
  - 最初の画面（B）：ボタンの下端は 1440px で 363px、390px で 398px。
  - uチャンネル未設定（C）：S09「高橋 健太さんの uチャンネルが未設定です」「ここからはハドルを始められません。Slack で高橋 健太さんに直接声をかけてください。」
  - ハーネスとの照合（D）：primary は全画面で 1 つ（S01〜S18 の目視）。
- **◎ とした理由**：クリック 1 回・スクロール 0 は、この構成で取りうる最小の手数。

### G3 先の予定を確かめられる ○

- **目標の瞬間**：予定を気にする人が「来週は誰か」「次のお休みはいつか」を知りたいとき。急ぎではない。
- **設計の意図**：
  1. 今週の情報（主役）を邪魔しないよう、別のカード「これからの予定」にまとめる。1440px では右列に置き、主役と同時に見えるようにする。
  2. 一番よく聞かれる 2 つ（次のお休み、各週の自分の相手）は**開かなくても見える**ようにし、全ペアは Collapse を開いたときだけ出す（whenToUse Collapse）。
  3. 先の週は確定ではないことを、「予定」の Tag と「参加する人が増えたり減ったりすると、組み直しになります」の注記で伝える。
  4. 祝日の週は「CT なし・スポーツの日」の Tag で区別する。
- **画面の要素**：「次のお休み：…」の行、注記、週ごとの Collapse（日付・Tag・「あなた：〇〇さん」）。
- **証拠**：
  - 最初の画面（B）：1440px では見出しの上端が 179px で最初の画面に入る。390px では 894px で、スクロールが要る（計測スクリプトで確認）。
  - 文言（C）：S01「次のお休み：11月2日の週まではありません」、S03「次のお休み：今週（10月5日（月））」、週ごとに「あなた：鈴木 翔太さん」など。
- **○ とした理由**：目的は果たせるが、390px ではスクロールが要る。主役を優先した結果で、意図した優先順位どおり。他人どうしのペアは開かないと見えない。「特定の人と次に当たる日」は入れていない。

### G4 誰が入っているかを確かめ、いなくなった人を安全に外せる ○

- **目標の瞬間**：まれに管理する人。退職者を外したいが、間違えて別の人を消したくない。
- **設計の意図**：
  1. 全体像を先に数字で見せる（参加 9・不参加 2・初回設定未完了 1）。その下に社員番号順の一覧。
  2. 参加・不参加は**色だけに頼らない**（チェック／マイナスのアイコン＋「参加」「不参加」の文字）。
  3. 削除は「取り消せない操作」なので、確認の Modal のタイトルに**誰を**消すかを書き（「加藤 大輔さんをメンバーから削除しますか？」）、本文に「元に戻せません」と「参加中なら組み直しになる」を書く。実行ボタンは danger で、文言は「削除する」（spec buttons「否定的な主操作は結果を強調」）。
  4. 休職中の人を誤って消さないよう、「休職中の人は本人が『参加しない』に変えられます」と別の手段を示す。
  5. 結果は必ず伝える。成功は message、失敗は見落とさないよう、モーダル内の Alert にする（spec feedback）。
  6. 自分自身は削除できない（自分の行には「設定を変える」だけ）。
- **画面の要素**：メンバー画面の Statistic、Listy、Tag、削除ボタン、確認の Modal。
- **証拠**：
  - 手数（A）：メンバー画面へ 1 → 「削除」1 → 「削除する」1 の計 3 クリック（`scripts/smoke.mjs` の「S11 → 削除 → 成功の通知」「削除後は一覧（11→10 人）」が PASS）。
  - 文言（C）：S13（確認）、S14（「削除できませんでした」＋「もう一度削除する」）、S12（0 人：「まだ誰もログインしていません」＋「Slack でログイン」）。
  - 機械検査（E）：S11・S13・S14 で axe の違反 0（参加状態の Tag の文字は 5.44:1）。
- **○ とした理由**：「安全に」の手段が確認モーダルだけで、取り消し（元に戻す）は無い。削除はログイン中の全員にできる（ブリーフどおり）。390px では 11 人で縦に長い。

### G5 自分の参加状況を変えられ、その影響が伝わる ○

- **目標の瞬間**：休職や繁忙期で抜ける、または戻る人。自分の変更が他の人に影響することを知らないまま変えてしまうおそれがある。
- **設計の意図**：
  1. 「参加する／参加しない（休職・繁忙期など）」を Radio.Group で並べ、2 つを見比べて選べるようにする。押した瞬間に反映される Switch は使わない（whenToUse Switch / Radio）。
  2. **選んだ直後、保存する前に**、選択肢のすぐ下に影響を出す（「保存すると、組み合わせから外れます」「今週以降の組み合わせが全員分組み直しになり、他の人の相手も変わります」「Slack に投稿済みの今週のペアとずれることがあるので、必要ならチャンネルで知らせてください」）。影響を知ったうえで「保存する」を押せる順番にした。
  3. 保存後はホームの主役カードが「CT に参加していないため、今週の相手はいません」＋「参加状況を変える」に変わり、自分の状態が一目でわかる。
- **画面の要素**：「自分の設定」の Radio.Group、warning の Alert、保存の message／Alert。
- **証拠**：
  - 最初の画面（B）・位置：`screenshots/G5-leave-warning-*.png`。警告の上端は 1440px で 645px、390px で 749px。「保存する」ボタンより上にある（ボタンの下端は 1440px で 821px、390px で 994px。`docs/g5-measure.txt`）。
  - 手数（A）：ヘッダーの「自分の設定」1 クリック → 「参加しない」1 → 「保存する」1 の計 3 クリック。390px では「保存する」までにスクロールが要る。
  - 通り道（E）：`smoke.mjs` の「参加しないを選ぶと影響の警告」「保存 → 成功の通知」が PASS。
  - 文言（C）：S10（「設定を保存しました」）、S17（「設定を保存できませんでした」「入力した内容はそのまま残っています」）。
- **○ とした理由**：影響は文で伝えるだけで、「誰の相手がどう変わるか」は示せない（組み合わせの計算をデモで実装していないため）。

### G6 初めての人が迷わず必要な設定を終えられる ○

- **目標の瞬間**：初めてログインした人。何を、なぜ入れるのかがわからないと止まる。
- **設計の意図**：
  1. 冒頭の一文で目的を伝える（「CT（毎週月曜 14:00 の 2 人 1 組の雑談）の組み合わせに入るために、次の項目を設定してください」）。
  2. 項目は 4 つだけ。名前は Slack の表示名、参加は「参加する」を既定値にして、**実際に入力が要るのは社員番号と uチャンネルの 2 つ**にする。
  3. 各項目の下に「何に使うか」を書く（spec research-form「わかりにくい語には補足を」）。uチャンネルは自由入力ではなく一覧から選ぶ。
  4. 手順は 1 画面で終わるので Steps は使わない。
  5. 未入力で送信したら、項目ごとに「社員番号を入力してください」のように、何をすればよいかの文を出す（spec feedback「入力フィードバックは対象の直後に」）。
  6. 完了したら組み合わせの画面に戻し、完了を伝える。
- **画面の要素**：「はじめての設定」画面のフォーム、項目ごとの補足とエラー。ホームの主役カードの「はじめての設定が済んでいません」＋「設定する」。
- **証拠**：
  - 文言（C）：S15（未入力。名前は「吉田 真央」が入っている）、S16（社員番号・uチャンネルにエラー）。
  - 通り道（E）：`smoke.mjs` の「S15 → 未入力で送信 → エラー」「初回設定の完了 → 組み合わせへ戻る」「完了後のパス」が PASS。
  - 手数（A）：入力 2 項目＋クリック 1 回（「設定を完了する」）。
- **○ とした理由**：初回ログイン時に自動で設定画面へ移す仕組みは無い。主役カードとヘッダーからの誘導に頼っている。

### G7 どんな状態でも、何が起きていて次に何をすればよいかがわかる ○

- **目標の瞬間**：全員。うまくいかないときに「壊れたのか」「待てばよいのか」「自分が何かすべきか」が分からないと止まる。
- **設計の意図**：どの状態でも「何が起きたか」と「次に何をするか」の **2 文を必ず出す**。部品は状態の重さに合わせて選ぶ（spec feedback・research-exception・research-empty）。
  - 一時的で軽いもの → message
  - 見落とすと困る失敗 → 消えない Alert
  - 画面全体が使えない → Result
  - データが無い → Empty ＋理由＋次の行動
  - 入力の誤り → 項目ごとのエラー
- **画面の要素と証拠**（すべて最終撮影で axe 違反 0）：

| 状態 | 部品 | 何が起きているか | 次の行動 |
| --- | --- | --- | --- |
| S05 | Empty（＋主役カードの説明） | 「CT に参加している人が 1 人のため、ペアを作れません」 | 「メンバーの参加状況を見る」 |
| S06 | Skeleton | 枠と見出しを先に出し、「組み合わせを読み込んでいます」 | 待つ |
| S07 | Result | 「組み合わせを読み込めませんでした」＋考えられる原因 | 「もう一度読み込む」 |
| S08 | Alert | 「Slack でログインできませんでした」＋考えられる原因 | 「もう一度ログイン」 |
| S12 | Empty | 「まだ誰もログインしていません」 | 「Slack でログイン」 |
| S14 | モーダル内の Alert | 「削除できませんでした」 | 「もう一度削除する」 |
| S16 | 項目ごとのエラー | 何が足りないか | 入力する |
| S17 | Alert | 「設定を保存できませんでした」「入力した内容はそのまま残っています」 | もう一度「保存する」 |
| S18 | Result | 「ページが見つかりません」 | 「組み合わせに戻る」 |

  通り道（E）：`smoke.mjs` の S07・S08・S17・S18 からの復帰がすべて PASS。

- **○ とした理由**：読み込み中（S06）に取り消しや時間の目安が無い（spec feedback は「長いときは取り消しを」とする）。S08 ではログインの導線が 3 つ（Alert・主役カード・ヘッダー）並び、どれを押すべきかがやや重複する。

## 4. G1・G2 の計測の詳細

`scripts/measure-g1g2.mjs` で、ビューポート 1440×900 と 390×900 で計測しました（結果は `docs/g1g2-measure.json`）。

## 5. 評価の限界

この評価は作り手自身による検査と計測で、次のことは測れていません。

| 測れていないこと | なぜ測れていないか | どう検証すべきか |
| --- | --- | --- |
| 実際の利用者が「すぐわかる」と感じるか（G1・G6） | 計測したのは手数と位置で、理解の速さではない | チームの数人に、月曜の状況を想定して Slack のリンクから開いてもらう。相手を答えるまでの秒数と、迷った箇所を観察する（5 秒テスト、初回設定のタスクテスト） |
| 影響の伝え方が十分か（G5） | 文言を作り手が読んだだけ | 「参加しない」を選んだ人に、何が起きると思うかを言ってもらう。誤解があれば文言を直す |
| 削除が「安全」か（G4） | 誤操作の頻度は測れない | 実運用での削除ログと、誤削除の問い合わせを記録する。必要なら「元に戻す」や権限の限定を検討する |
| スクリーンリーダー・キーボードだけでの操作 | axe は機械的に判定できる規則だけを見る。読み上げの順序や内容のわかりやすさ、フォーカスの移動は人が確かめる必要がある | VoiceOver（iOS / macOS）と NVDA で、主役カード → ハドル開始、削除の確認、初回設定を操作する。Tab キーだけで同じ操作を行い、フォーカスの位置が見えるかを確かめる |
| 実機のスマートフォン | 390px のビューポートで代用した。実機のツールバー、文字の拡大設定、Slack アプリ内ブラウザは試していない | iPhone・Android の実機と Slack アプリ内ブラウザで開き、最初の画面とボタンの押しやすさを確かめる。OS の文字サイズを大きくした状態でも確かめる |
| 実際の Slack との連携 | ログインとハドル開始はデモの通知だけ | Slack の OAuth とハドルの起動（URL スキームなど）を実装してから、手数を数え直す |
| 色の見分け（色覚の多様性） | axe は対比だけを見る | 色覚シミュレーション（Chrome DevTools の Rendering）で、頭文字アバターの色と状態の Tag を確かめる。状態は文字とアイコンでも区別しているが、アバターの色は色だけに頼っている |
| 評価者の偏り | 設計した本人が評価しているため、意図どおりに見えやすい | 設計に関わっていない人に、この文書の基準で同じ画面を評価してもらい、評価記号を比べる |
