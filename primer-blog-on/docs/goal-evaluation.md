# 目標の評価（O1〜O4）

## 1. 評価の方法

利用者による検証はしていない（できない）。代わりに、次の 3 つの基準で「画面が目標を満たしうるか」を論証する。

| 基準 | 中身 | 選んだ理由 |
| --- | --- | --- |
| A. 到達の手数 | その目標に要る情報が、**最初に開く画面（`/`）から何操作で見えるか**。0 操作（開いただけで見える）を最良とする | O3・O4 は「忘れない」「早く気づく」で、探しに行かないと見えない情報は気づかれない。手数は画面から数えられる |
| B. 固定データでの再現 | fixtures.ts に仕込まれた事実（id=6 の遅れ、11/23 週の取りやめのみ、id=9・10 の予定なし、id=1 の担当 2 件）が、**画面上に文字として出ているか**をスクリーンショットで確認 | ブリーフの固定データは「気づくべきこと」をわざと含んでいる。それが表示されなければ目標に届かない |
| C. 知覚の頑健さ | 色だけに頼らず文字で伝わっているか、390px でも同じ情報が出るか、axe（WCAG 2.1 AA）違反と横はみ出しが無いか | スマホで開く書く人（I01 の仮定）と、色の見分けに頼れない人にも同じ情報が届く必要がある |

証拠のファイル：`screenshots/`（撮影は `scripts/capture.mjs`、ブリーフの `brief/scripts/capture.mjs` と同一内容）、`docs/evidence/capture-final.txt`（axe と横はみ出し）、`docs/evidence/smoke-test.txt`（操作の確認）。

## 2. 目標ごとの論証

### O1 社内ブログを、週 1 本以上のペースで途切れずに公開し続ける

- **意図**：週 1 本を下回る週を、公開の前に見つけて埋められるようにする。
- **画面の要素**：
  - 計画（`/`）の**週の列**：期間内の全週を 0 件でも行として出す。各週の見出しに「公開 n 本・予定 n 本」。
  - 0 件の週：Label「予定なし」＋「この週は投稿予定がありません。」＋「この週に投稿予定を登録」（予定日を週の月曜で埋めた登録画面へ）。
  - 期間の要約「8 週のうち 7 週に投稿予定・公開があります」。
- **証拠**：
  - A：0 操作。`S01-plan-member-1440.png` の最上部 Banner に「投稿予定が入っていない週：11/23〜11/29」、週の列の 11/23 行に「予定なし」。
  - B：11/23 週は取りやめ（id=15）のみだが「予定なし」と判定され、取りやめの行は打ち消し線付きで同じ週に残る（`S01`）。`S08-plan-12weeks`（10/5〜12/27）では 12/21 週も「予定なし」になる。
  - 操作：`S37-new-editor-weekprefill` で公開予定日が 2026-11-23 で埋まった登録画面。
- **弱いところ**：「週 1 本」は数え方を示すだけで、2 本ある週から空き週へ移す提案などはしない。

### O2 書く人や時期の偏りを減らす

- **意図**：書いていない人と、詰まっている／空いている時期を見えるようにする。
- **画面の要素**：書く人ごとタブの表（全 10 人、予定も公開も 0 の人を先頭に Label「予定なし」）、表の上の「期間内の公開も、これからの予定も無い人：2 人（中村 彩、加藤 大輔）」。時期の偏りは計画の週見出しの本数。
- **証拠**：
  - A：1 操作（タブ「書く人ごと」）。
  - B：`S17-authors-member-1440.png` で中村 彩・加藤 大輔が先頭、Label「予定なし」。fixtures のコメント「id=9 … と id=10 … は、今のところ書く予定のある投稿が無い」と一致。伊藤 葵・田中 遥は期間内公開 1 本で、公開が 2 人に寄っていることも読める。
  - C：390px では表だけが横にスクロールし（ScrollableRegion）、ページの横はみ出しは 0（`capture-final.txt`）。
- **弱いところ**：時期の偏りはグラフではなく数字の並びでしか見えない。「偏っている」という判定（例：4 週で同じ人が 2 本）は出していない。

### O3 書く人が、自分の担当と予定日を忘れない

- **意図**：自分の担当と「あと何日か」を、探さずに目に入れる。
- **画面の要素**：
  - 計画の上部「あなたの担当：アクセシビリティ改善の振り返り（11/12（木）・あと 3 日）」。
  - 計画の各行の Label「あなたの担当」。
  - タブ「自分の担当」（未公開件数 2 の counter）：予定日が決まっている投稿（遅れが先頭）→ 日付未定 → 公開済み・取りやめ。
- **証拠**：
  - A：0 操作（計画の上部の 1 行とタブの counter）。一覧は 1 操作。
  - B：id=1 の担当は id=3（公開済み・共著）、id=7（レビュー中・11/12）、id=14（日付未定）。`S11-mine-member` で 3 グループに分かれて出る。
  - C：「あなたの担当」は Label の文字で示し、色だけに頼らない。390px でも同じ。
  - 未ログインでは `S12-mine-guest` で「ログインすると、あなたの担当が表示されます」。
- **弱いところ**：アプリを開かなければ何も届かない（Slack 通知はブリーフで「デモでは通知を出すだけ」とされ、リマインドは実装していない）。O3 にいちばん効くのは本来リマインドで、画面だけでは限界がある。

### O4 取りまとめ役（編集担当）が、計画の抜けや遅れに早く気づける

- **意図**：開いた瞬間に「対応が要るもの」が一番上に出る。
- **画面の要素**：計画の最上部の Banner（warning）「要対応：予定日を過ぎた投稿 1 件、予定の無い週 1 週」。中身は遅れの記事へのリンク（書く人・遅れ日数付き）と空き週の一覧。行の Label「4 日遅れ」。書く人ごとの「遅れ」列。
- **証拠**：
  - A：0 操作（`S03-plan-editor-1440.png`）。
  - B：id=6「テストの書き方ガイドライン（仮）」（予定 11/5・執筆中）が「4 日遅れ」で Banner と 11/2 週の先頭に出る。
  - 操作：smoke test で id=6 を削除すると Banner から遅れが消える（`docs/evidence/smoke-test.txt`「overdue banner gone: true」）。
  - C：Banner は見出し付きの region で、遅れは「4 日遅れ」の文字で伝わる。
- **弱いところ**：「近い予定（7 日以内）」は要約文の件数だけで、Banner には入れていない（入れると常に何かが出て警告が効かなくなると判断）。

## 3. 状態の検査結果（C の一部）

- 45 状態 × 2 幅（1440／390）＝ 90 枚。最終結果は `docs/evidence/capture-final.txt`。1 回目は週の列で `list(1) listitem(8〜12)`（`<ol>` と `<li>` の間に Stack の `div` が入っていた）を検出し、`Stack as="ol"` に直して 2 回目以降 0 件（`capture-run1.txt` → `capture-run2.txt`）。横はみ出しは 1 回目から全状態 0。
- 撮影を見て直したもの：詳細画面の「計画に戻る」が広い画面で出ていなかった（PageHeader.ContextArea の既定が狭い画面のみ表示）、削除ダイアログが狭すぎた（width を large に）、390px で操作ボタンにタイトルが押しつぶされた（ボタンを本文の先頭に移動）。

## 4. 評価の限界

- **利用者がいない**。手数・表示の有無・機械検査は「気づける画面になっているか」の必要条件で、実際に気づくか・行動するかは測れていない。
- 基準 A〜C は自分で選んだもので、ハーネスに評価方法の記述は無い（Primer のパターンは「どう作るか」で「目標に届いたかの測り方」ではない）。
- axe は自動検出できる違反しか見ない。キーボード操作・読み上げの順序は smoke test でフォーカス移動の一部（誤りのある項目へのフォーカス）を確かめただけ。
- 固定データ 15 件・10 人での確認で、投稿が 100 件を超えたときの週の列の長さや表の読みやすさは未確認。
- 「今日」は固定（2026-11-09）。実際の日付で動かしたときの境界（年またぎ・週の始まり）は単体テストをしていない。
