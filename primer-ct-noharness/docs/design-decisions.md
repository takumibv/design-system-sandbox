## 0. 前提として決めたこと

- **利用の中心は「月曜の数十秒」**。ブリーフ「月曜の CT 前に『今週の相手は誰か』を確かめ、そのまま相手との通話（Slack ハドル）を始める。滞在は数十秒で終わる。」から、トップ画面は「自分の相手」と「ハドル開始」の 2 点に最短で届くことを最優先にする。管理系（削除・設定）はトップから外す。
- **Slack 投稿からのリンク先になる**＝スマートフォンで開かれることが多いと推測する（推測）。390px でもファーストビューに G1・G2 が収まることを条件にする。
- **画面は 3 つ＋404**：
  1. 組み合わせ（`/`）…トップ。今週と先の週。
  2. メンバー（`/members`）…一覧・削除。
  3. 自分の設定（`/settings`）…通常の設定。初回設定は同じフォームを専用の見出し・説明つきで `/setup` に出す。
  4. 404（その他のパス）。
- ナビゲーションは、上部の共通ヘッダー（ロゴ・サービス名・ログイン状態）の下に、画面切り替えのタブ型ナビゲーション（`UnderlineNav`）を置く。画面が 3 つしかなく横並びで足りるため、サイドバー（`NavList`）は使わない。

## 1. 目標ごとの達成手段（下書き）

### G1 開いてすぐ「今週、自分は誰と話すか」がわかる

- **画面**：組み合わせ（トップ）。
- **要素**：ページ見出し「今週の組み合わせ」の直下に、「あなたの今週の相手」の枠（Primer の `Card`。experimental から）を置く。中に相手の大きめのアバター（48px）・名前（見出し級）・日時（10月5日（月）14:00〜）。
- **根拠**：ブリーフ「ログイン中なら、自分のペア（またはお休みであること）を探さずにわかる」。全員のペア一覧の中から探させると、9〜11 人程度でも視線移動が生じる。一覧の前に「答え」だけを出す。
- お休みの週（S03）は同じ枠に「今週はお休みです」と次の CT の相手を出す。祝日（S04）は「今週は CT なし（スポーツの日）」と次回の相手を出す。
- 未ログイン（S02）は同じ枠の位置に「ログインすると、ここにあなたの相手が出ます」とログインボタンを出す（G1 の場所を学習させる）。

### G2 その相手との通話をすぐ始められる

- **要素**：上記の枠の中に、そのページで唯一の主ボタン（`Button variant="primary"`）「ハドルを始める」。下に「#u-misaki で始めます」と場所を明記。
- **どちらの uチャンネルか（ブリーフで未決）**：**ペアのうち社員番号が若い人（並びで左側の人）の uチャンネルに集合**と決める。理由：2 人がそれぞれ「相手の」チャンネルを開くと、別々のハドルを同時に始めてしまい会えない。1 ペア 1 か所に固定し、両者に同じ場所を示せば行き違いが起きない。全員のペア一覧にも同じ場所を示す。
  - 弱点：ブリーフの「相手の uチャンネル」という表現とは、自分が左側の人の場合に食い違う（自分のチャンネルになる）。文言を「#u-misaki で始めます」と場所そのもので示し、「相手の」とは書かない。
- uチャンネル未設定の人がいるペア（S09）は、ボタンを出さず、理由と代わりの手段（Slack で直接声をかける）を `InlineMessage`（warning）で示す。

### G3 先の週の予定を確かめられる

- **要素**：1440px では右の欄（`PageLayout.Pane`、右側）に「これからの予定」を週ごとに縦に並べる。390px では本文の下に続く。
- 各週：日付（曜日つき）、ラベル「予定」、ログイン中なら「あなたの相手」の 1 行、全員のペアは開閉（`Details`）の中。祝日の週は「CT なし（祝日名）」。
- 欄の先頭に「あなたの次のお休み」を 1 行で出す（ブリーフ G3「次にお休みになるのはいつか」への直接の答え）。
- **範囲**：固定データにある今週＋4 週（11月2日まで）をすべて出す。「それより先は、参加者が変わると大きく変わるため出していません」と書き添える（推測に基づく判断）。
- 「先の週は予定」の伝え方：欄の説明文（「参加者が増減すると組み直されます」）と、各週のラベル「予定」の 2 か所。

### G4 誰が組み合わせに入っているかを確かめ、いなくなった人を安全に外せる

- **画面**：メンバー（`/members`）。
- **要素**：表（experimental の `DataTable`）。列は「メンバー」「参加状況」「操作」。参加状況はラベルの**文字**（「参加」「不参加」）で区別し、色は補助。初回設定未完了の人には別のラベル「初回設定が未完了」。
- 表の見出しの説明に「参加 9 人・不参加 2 人（全 11 人）」。
- 削除は行ごとの「削除」ボタン（危険操作なので `danger` 系ではなく通常の見た目のアイコン付きボタンにし、確認ダイアログの確定ボタンだけを `danger` にする）。確認は `ConfirmationDialog`。初期フォーカスはキャンセル（型定義 `ConfirmationDialog.d.ts` のコメント「危険な操作ではキャンセルに初期フォーカス」をそのまま使う）。
- **削除の権限（ブリーフで未決）**：ログイン中の全員に許す。ただし自分自身の行には削除ボタンを出さない。理由：ブリーフの要件「ログイン中の人はメンバーを削除できる（退職者など）」をそのまま採る。管理者の概念はブリーフにない。自分を消す操作は意味が薄く事故のもと。
- 結果は表の上に `Banner`（成功＝success／失敗＝critical）で出し、そこへフォーカスを移す。失敗時は「もう一度試す」を付ける。

### G5 自分の参加状況を変えられ、その影響が伝わる

- **画面**：自分の設定（`/settings`）。メンバー一覧の自分の行と、ヘッダーのユーザーメニューから入れる。
- **要素**：フォーム内の `Checkbox`「CT に参加する」。保存ボタンで確定するフォームなので、即時反映を想起させる `ToggleSwitch` は使わない（事前知識：Primer では ToggleSwitch は即時に効く設定向け、フォームで後から送信するものは Checkbox という慣習。確信度：中）。
- **影響の伝え方**：常時の説明（Caption）「参加をやめる・戻ると、全員の組み合わせが組み直されます」に加え、**値を変えた瞬間に**チェックボックスの直下へ `InlineMessage`（warning）で「保存すると、今週（10月5日）以降の全員の組み合わせが組み直されます」。保存後の成功 Banner でも同じことを繰り返す。

### G6 初めての人が迷わず必要な設定を終えられる

- **画面**：初回設定（`/setup`）。初回ログイン直後はここへ移す。ほかの画面にいるときも、未完了なら上部に `Banner`（warning）「初回設定が終わっていません」と「設定する」ボタンを出す。
- **要素**：見出し「はじめに、3 つの項目を設定してください」。名前は Slack の表示名を初期値に。社員番号は半角数字（`inputMode="numeric"`）。uチャンネルは `Select` で既存一覧から選ぶ。参加は初期値「参加する」。
- 必須表示：各ラベルに必須の印（`FormControl required`）＋フォーム冒頭に「すべて必須です」。
- エラー：送信時に検証し、各項目の下に `FormControl.Validation`、フォーム上部にエラーの要約 `Banner`（critical）、最初のエラー項目へフォーカス。

### G7 どんな状態でも、何が起きていて次に何をすればよいかがわかる

| 状態 | 部品 | 次の行動 |
| --- | --- | --- |
| 読み込み中 | `Spinner` ＋文言（「組み合わせを読み込んでいます」） | 待つ |
| 読み込み失敗 | `Banner` critical | 「もう一度読み込む」 |
| ログイン失敗 | `Banner` critical（ページ上部） | 「もう一度ログイン」 |
| 参加者 2 人未満 | `Blankslate` | 「メンバーを見る」 |
| メンバー 0 人 | `Blankslate` | 「Slack でログイン」 |
| 保存成功／失敗 | `Banner` success／critical | 失敗時「もう一度保存」 |
| 404 | `Blankslate` | 「組み合わせに戻る」 |

## 2. 全体の方針

- **主ボタンは 1 画面に 1 つ**（事前知識：Primer の Button の慣習。確信度：中）。トップ＝「ハドルを始める」（未ログイン時は「Slack でログイン」）、設定＝「保存する」、メンバー＝なし（削除確認ダイアログ内の確定は danger）。
- **色**：主ボタンは Primer の primary（緑）。状態色は Primer の意味色（success／attention／danger）を `Label`・`Banner`・`InlineMessage` 経由でだけ使う。自分の強調は accent（青）系の muted 背景。アバターの人ごとの色は `@primer/primitives` の display 色（blue／green／purple／orange）。
- **自前の CSS**：原則なし。ただし次は Primer に該当部品がないため、トークン（CSS 変数）だけを使って書く予定：
  1. 頭文字アバター（`Avatar` は `src` が必須で頭文字の代替表示がない：`Avatar.d.ts`）。
  2. 自分のペアの行の強調背景。
  3. ヘッダーのロゴ画像の高さ。
- **ログイン・ハドルのデモ動作**：ブリーフ「デモでは通知を出すだけでよい」。ログインは id=1 としてログインした状態に切り替え、ページ上部に `Banner`（info）で「（デモ）」と明記した通知を出す。ハドルは通知のみ。
- **参加者数の数え方（ブリーフで未決）**：「参加者」は参加中かつ初回設定済みの人だけ（固定データでは 9 人）。トップには「参加者 9 人」と出し、メンバー画面では「参加 9 人・不参加 2 人（全 11 人）」と両方出す。理由：トップで知りたいのは「組み合わせに入っている人数」で、奇数ならお休みが出ることとつながるため。
- **「特定の人と次に当たる日」（ブリーフで未決）**：専用の検索機能は入れない。先の週の欄に各週の「あなたの相手」を 1 行ずつ並べるので、表示範囲（5 週）内なら目で追える。数十秒の利用で使われる頻度が低いと判断（推測）。
- **社員番号**：固定データに社員番号がないため、id の順を社員番号の順とみなし、デモの社員番号は `1000 + id` とする（仮定）。
- **文言**：です・ます調。ボタンは「〜する」「〜を始める」の動詞で終える。見出しは名詞止め。

### 変えたこと

| 下書き | 実装 | 理由（根拠の種類） |
| --- | --- | --- |
| ナビは `UnderlineNav`（アイコン付き） | アイコンは狭い幅で自動的に隠す（既定の `hideIconsBreakpoint`） | 390px でアイコンを出したままにすると 3 つ目の「自分の設定」が英語の「More」メニューに入ってしまった（撮影で確認。その他の自分の判断） |
| ヘッダーの下に区切り線 | `PageLayout.Header` の区切り線をやめ、`UnderlineNav` の下線だけにした | 線が 2 本重なって見えた（撮影で確認） |
| 先の週の全員のペアは `Details` で開閉 | `Details` の中の summary を `Button as="summary"`（invisible・小・下向き矢印）にした | `Details.Summary` だけでは開閉できることが見た目でわからなかった（撮影で確認） |
| メンバー表は 3 列 | 狭い幅（`useResponsiveValue` の narrow）では「メンバー・参加状況」を 1 列にまとめ、操作列と 2 列にした | 390px で操作列（削除）が表の外へはみ出し、表の中だけで横スクロールしていた。ページ全体の横はみ出し検査（overflow）は 0 だったので検査では見つからず、撮影を目で見て気づいた |
| 祝日の週の見出し行も「14:00 開始」 | 「2026年10月12日（月）は CT なし（スポーツの日）」 | 撮影で「CT なし」と「14:00 開始」が同じ画面に並んで矛盾していた |
| 「あなたの次のお休み」を常に出す | 先の週にペアが 1 組もないとき（S05）は出さない | 組み合わせがないのに「お休みの予定なし」と出ると誤解を招く |
| エラー要約「赤い文字の説明に沿って」 | 「各項目の下に出ている説明に沿って」 | 色だけに頼った指示になっていた（一般的なアクセシビリティの知識） |

### 実装で決めたこと

- **状態の開き方**：`?state=S01`〜`S17` のクエリで最初の状態を決める。画面の切り替え（パス）は `/`・`/members`・`/settings`・`/setup`。S18 は存在しないパス `/no-such-page`。画面を移るとクエリは外れ、以後はふつうに操作できる（ログイン・削除・保存もデモとして動く）。
- **S04（祝日の週を表示中）**：「祝日の週が今週である」状態として開く（今週＝10月12日）。通常の S01 でも右の欄に祝日の週（10月12日）が出ている。
- **S14（削除に失敗）**：確認ダイアログで「削除する」を押して失敗した直後として開く。S14 で開いたあとに削除を試しても、毎回失敗する。
- **S17（保存に失敗）**：保存を押して失敗した直後として開く。入力は残り、「もう一度保存する」で再送できる（このデモでは再送も失敗する）。
- **初回設定のあと**：組み合わせは固定データのため、初回設定を終えても組み合わせには反映されない（デモの限界）。成功の Banner で「組み直され、あなたも入ります」と伝えるだけにした。
- **読み込み中**：`Spinner` だけだと何を待っているかわからないので、文言「組み合わせを読み込んでいます…」を並べ、`role="status"` で読み上げさせる。`Spinner` の `srText` は文言と重複するので `null`（型定義 `Spinner.d.ts` のコメント「ページ内の別のテキストで示す場合は null」による）。
- **通知（ログイン・ハドル・ログアウトのデモ）**：ページ上部の `Banner`（info）。出たらフォーカスを移す。閉じるボタンつき。

### 自前の CSS（`src/styles.css`）と理由

すべて `@primer/primitives` の CSS 変数（トークン）だけで書いています。色・余白・角丸の値を直接書いた箇所はありません（頭文字アバターの大きさだけ、`size` の数値からインラインの `style` で幅・高さ・文字サイズを決めています）。

| # | クラス | 何のために | Primer に無かったもの |
| --- | --- | --- | --- |
| 1 | `.initials` | アイコンが無い人の頭文字アバター。人ごとの色は display 色（blue／green／purple／orange）の muted 背景＋文字色 | `Avatar` は `src: string` が必須で、頭文字の代替表示が無い（`Avatar/Avatar.d.ts`） |
| 2 | `.logo` | ヘッダーのロゴ画像の高さ（24px）| 画像の大きさを決める部品が無い |
| 3 | `.plainList` | `ul` の点と余白を消す | 素の一覧部品が無い（`ActionList` は操作の一覧向けと理解しているため使わなかった。事前知識） |
| 4 | `.pairRows`・`.pairRow` | ペアの一覧の枠・区切り線、自分のペアの強調（accent の muted 背景＋左の太線） | 行の強調を持つ一覧部品が無い（v38 では `Box` も無くなっている：`index.d.ts` に export が無いことを確認） |
| 5 | `.muted` | 補足の文字色（fgColor-muted） | v38 の `Text` に色の指定が無い（`Text/Text.d.ts`） |

### 使わなかったもの

- `Header`（GitHub の黒いヘッダー）：Gaji-Labo のサービスであることを示したいので、GitHub らしさの強い黒帯は避けた（事前知識：`Header` は GitHub.com の上部の黒いバー。確信度：中）。
- `ToggleSwitch`：保存ボタンのあるフォームの中なので `Checkbox` にした（G5 参照）。
- `Flash`：古い通知部品で、今は `Banner` が推奨されていると記憶している（事前知識。確信度：中）。
- `Dialog` を自前で組む：削除の確認は `ConfirmationDialog` で足りる。
