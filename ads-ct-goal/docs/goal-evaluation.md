# 目標の自己評価（G1〜G7）

## 1. 評価の方法

### 自分で決めた評価基準

| 観点 | 基準 | この基準を選んだ理由 |
| --- | --- | --- |
| 操作量（G1・G2・G4〜G6） | 目的を果たすまでのクリック・入力の回数と、必要なスクロール量（px）を **1440×900 と 390×900** で数える | ブリーフの利用シーンは「数十秒で確認して通話」。時間を左右するのは操作の回数と探す量なので、直接数えられるものを使った |
| ファーストビュー（G1・G2・G7） | 必要な要素の下端が 900px 以内に入るか（`scrollNeeded = max(0, 下端 − 900)`） | 「探さずにわかる」を、スクロールなしで目に入ることと定義した |
| キーボード（G2） | ページ読み込みから「ハドルを始める」に Tab で何回で届くか | マウスを使わない人の操作量の目安 |
| 状態の伝わり方（G5〜G7） | 各状態の画面に「何が起きたか」と「次の行動（ボタンや具体的な手順）」の両方があるか。文言を状態ごとに読んで確認 | ADS のメッセージ設計（原因＋次の行動、行き止まりを作らない）に合わせた |
| ハーネスとの照合 | 使った部品が ADS の usage／content ガイドラインの「使う場面」に合っているか（`design-decisions.md` §4、`harness-report.md` §3） | ADS らしさの根拠 |
| 機械的な検査 | axe（WCAG 2.1 A／AA）の違反数、横はみ出し、ADS 公式 lint の件数 | 自己判断に頼らない下限 |

### 計測の仕組み

- `scripts/measure.cjs`（Playwright。本番ビルドを `vite preview` で配信）→ 結果 `docs/measurements.json`
- `scripts/capture.mjs`（ブリーフの撮影スクリプトの無改変コピー）→ `screenshots/Sxx-1440.png`／`Sxx-390.png`、`screenshots/report.json`、`docs/capture-report.txt`
- lint：`harness-logs/lint/eslint-recommended.txt`（0 件）、`eslint-all.txt`（警告 4 件）

### 機械的な検査の結果

- axe（wcag2a・wcag2aa・wcag21aa）：**18 状態 × 2 幅 = 36 画面すべて違反 0**
- 横はみ出し：**36 画面すべて 0px**
- ADS lint：推奨設定 **0 件**（修正前は警告 7 件）、全ルール **警告 4 件**（Lozenge の新しい appearance 名への移行。現行の型が受け付けないため保留。`harness-report.md` §5）

## 3. 目標ごとの論証

### G1 開いてすぐ「今週、自分は誰と話すか」がわかる

- **設計上の意図**：利用者は月曜に Slack の投稿から来て数十秒で去る。だから画面の主役は「今週のあなたの相手」ひとつに絞り、ページの最上部に置く。他の情報（全員のペア、先の週）は主役の下に回す。ハーネスからは「大きさと余白で順位をつける」「すべてを同じ重さにしない」を借りた（主役の選定そのものは自分の判断）。
- **画面の要素**：`今週の CT` 見出しの直下に、太い brand 色の枠（`border.width.selected`／`color.border.brand`）のカード。xlarge のアバター、`Heading xlarge` の「高橋 健太さん」、「14:00 から」。日付と開始時刻は見出しの下に 1 行。
- **証拠**：S01-1440.png／S01-390.png。名前の下端は 1440px で 281px、390px で 365px（`measurements.json` の `S01.partnerName`）。どちらもスクロール 0・操作 0。
- **他の状態**：自分がお休み（S03）は同じ場所に「今週はお休みです」と次の CT（10月19日、小林 結衣さん）。祝日の週（S04）は「今週は CT がありません」と祝日名と次の CT。どちらも主役の場所を変えないので、見る場所が一定。

### G2 その相手との通話をすぐ始められる

- **設計上の意図**：相手の名前の直下（近接）に、ページで唯一の primary ボタンを置く。押したときにどこへ行くか不安が無いよう、ハドルの場所（#u-misaki）を書く。2 人が別々のチャンネルでハドルを始めてしまわないよう、場所は「ペアのうち社員番号が小さい人の uチャンネル」に決めた。
- **画面の要素**：「ハドルを始める」（primary、ヘッドホンのアイコン）と「#u-misaki で始まります。高橋 健太さんも同じチャンネルに入ります。」
- **証拠**：ボタンの下端は 1440px で 375px、390px で 459px（スクロール 0）。クリック 1 回で「#u-misaki でハドルを始めます（デモ）」の Flag が出る（`huddleFeedbackShown: true`）。Tab 7 回で届く（ロゴ → ナビ 3 つ → ログアウト → メンバーを見る → ハドル）。未ログイン（S02）では同じ場所の「Slack でログイン」から 2 クリック。
- **相手の uチャンネルが未設定（S09）**：ボタンを出さず、同じ場所に warning の SectionMessage「ハドルを始められません」と、代わりの行動（Slack で直接連絡）。警告の見出しの下端は 1440px で 379px、390px で 463px。

### G3 先の週の予定を確かめられる

- **設計上の意図**：「来週は誰か」「次のお休みはいつか」は自分にしか関係しないので、全員の表から探させず、自分だけの 1 週 1 行のリストにする。先の週は確定ではないので「予定」と書き、組み直しがあることを一文で添える。
- **画面の要素**：「あなたの今後の予定」（1024px 以上は主役の右、未満は主役の下）。各行に日付・Lozenge（来週・予定／予定／CT なし）・相手。冒頭に「次のお休み：…」。全員分は「今後の予定」セクションに週ごと。
- **証拠**：最終行の下端は 1440px で 421px、390px で 829px（スクロール 0）。S03 では「次のお休み」の表示と主役カードの「次の CT」で先の予定がわかる。
- **○ にした理由**：見せる範囲は 4 週先まで（固定データの範囲）。全員分の先の週は 390px だと長いスクロールになる。

### G4 誰が組み合わせに入っているかを確かめ、いなくなった人を安全に外せる

- **設計上の意図**：一覧は社員番号順、参加／不参加／初回設定未完了を Lozenge（文字つき）で区別。人数は見出しの下に「参加 9 人・不参加 2 人」と文で書く。削除は取り消せないので、Modal で「誰を」（アバター・名前・チャンネル）「何が起きるか」（参加者なら組み合わせが組み直される）「取り消せない」を書き、danger の「削除する」で確定。結果は Flag。
- **証拠**：S11（一覧）、S13（確認）、S14（失敗 Flag、「もう一度削除する」つき）。組み合わせ画面から 3 クリックで削除完了、成功 Flag を確認（`G4.successFlag: true`）。各削除ボタンのアクセシブルな名前は「○○さんを削除」。
- **○ にした理由**：390px では一覧の下の方の人までスクロール（415px）が要る。削除権限を全員に許したのは自分の判断で、運用で確かめる必要がある。

### G5 自分の参加状況を変えられ、その影響が伝わる

- **設計上の意図**：影響は「保存した後」ではなく「保存する前」に伝える。チェックを変えた瞬間に、すぐ下へ warning の SectionMessage を出す（ADS：warning は将来起きる変化の事前通知）。保存後は組み合わせ画面に戻し、主役カードが変わったことを見せる。
- **証拠**：組み合わせ画面から 3 クリック。チェックを外した時点で警告が出る（`warningShownBeforeSave: true`）。保存後は `/` に戻り、成功 Flag と「今週の組み合わせに入っていません」（`heroAfterLeaving: true`）。S17 は保存失敗時、入力を残したまま「もう一度保存する」。
- **○ にした理由**：固定データを使うため、他の人のペアの組み直しは画面に出ない。

### G6 初めての人が迷わず必要な設定を終えられる

- **設計上の意図**：初回ログインした人には組み合わせ画面の代わりに「はじめての設定」を出す。冒頭で「何のための設定か」「終わると何が見えるか」を書く（ADS の新規ユーザー向けの語調）。名前は Slack の表示名で埋めておき、入力は 2 つだけ。送信ボタンは無効化せず、足りない項目は送信時に項目ごとに知らせる。
- **証拠**：S15（未入力）、S16（送信後のエラー：「社員番号を入力してください」「uチャンネルを選んでください」、最初のエラー項目にフォーカス）。入力 2＋送信 1 で完了し、組み合わせ画面に戻って成功 Flag（`G6.backOnHome: true`、`successFlag: true`）。送信ボタンはスクロール 0。
- **○ にした理由**：完了直後の主役カードは「今週の組み合わせにはまだ入っていません」（組み直し待ち）で、設定を終えても今週の相手はすぐには見えない。冒頭の文言は実装後の確認でこの挙動に合わせて直した（「次に組み合わせが組み直されたときから…表示されます」）。

### G7 どんな状態でも、何が起きていて次に何をすればよいかがわかる

| 状態 | 何が起きているか（画面の文言） | 次の行動 |
| --- | --- | --- |
| S05 参加者が 2 人未満 | 「今週の組み合わせはありません」「参加者が 1 人のため、組み合わせを作れません」 | 「メンバーを見る」 |
| S06 読み込み中 | Spinner＋「組み合わせとメンバーを読み込んでいます…」 | 待つ |
| S07 読み込み失敗 | 「組み合わせを読み込めませんでした」 | 「もう一度読み込む」、続くときは Slack の投稿を確認 |
| S08 ログイン失敗 | 「Slack でログインできませんでした」 | 「もう一度ログインする」。組み合わせはそのまま下で見られる |
| S09 相手の uチャンネル未設定 | 「ハドルを始められません」と理由 | Slack で直接連絡 |
| S12 メンバー 0 人 | 「まだメンバーがいません」 | 「Slack でログイン」 |
| S14 削除失敗 | 「加藤 大輔さんを削除できませんでした」「一覧はそのまま」 | 「もう一度削除する」 |
| S16 必須未入力 | 項目ごとのエラー | 入力して再送信 |

- **証拠**：各状態のスクリーンショット（1440／390）。失敗系の表示はすべて 1440px・390px のファーストビュー内。

## 4. 評価の限界

| 測れていないこと | なぜ問題か | どう検証すべきか |
| --- | --- | --- |
| 実ユーザーでの確認 | 「迷わない」「すぐわかる」は本人の感じ方。計測はクリック数と位置だけ | 月曜の CT 前に 5〜8 人へ、Slack の投稿からの操作を観察（ハドル開始までの時間、迷った箇所） |
| スクリーンリーダー | axe は構造の機械検査だけ。読み上げ順や Flag の通知が自然かはわからない | VoiceOver（iOS／macOS）と NVDA で S01・S09・S13・S16 を操作。Flag の読み上げ、Modal のフォーカス移動、エラーの通知を確認 |
| 実際の Slack 連携 | ハドル・ログインはデモの通知だけ | Slack のディープリンクで、ペアの 2 人が同じハドルに入れるかを実機で確認 |
| 組み合わせの組み直し | 固定データのため、参加の変更や削除の影響（他の人のペアの変化）を画面で示せていない | 計算を実装し、変更前後の差分を見せる案を検討 |
| アイコン画像がある人 | 固定データに画像が無く、頭文字の表示しか確認していない | 画像あり・読み込み失敗の両方を撮影 |
| 200% 拡大・ダークモード | 撮影条件に含まれない | ブラウザ拡大と `colorMode: "dark"` で撮影 |
| 自己評価の偏り | 設計者自身が評価している | 別の人（または別のエージェント）にブリーフだけ渡して評価してもらう |
