# 設計判断：目標 O1〜O4 をどこで達成するか

実装の前に書いた。情報構造は `information-architecture.md`。根拠の記号は同じ（［H］ハーネス、［B］ブリーフ、［仮定］、［判断］）。

## 目標と画面要素の対応

| 目標 | 意図（どう効かせるか） | 画面・要素 | 根拠 |
| --- | --- | --- | --- |
| **O1** 週 1 本以上を途切れずに公開し続ける | ① 「週」を単位に計画を見せ、**本数が 0 の週がその場で目立つ**ようにする ② 先の週まで見えるようにして、空く前に埋められるようにする | V1 投稿計画：今週の 2 週前〜7 週先の 10 週を週ごとに並べる。各週の見出しの横に「n 本」。**取りやめを除いて 0 本の週**は、その週の中に警告（アイコン＋「この週は投稿予定がありません」）を出す。見出し領域の「確認が必要なこと」に、今週以降の予定の無い週を列挙する。期間は開始日〜終了日で変えられ、「前の期間／次の期間」で 10 週ずつ送れる | 週を単位にするのは O1 の文言から［B］。概念モデルで「週」を重要概念に置いた（`information-architecture.md` 2 章）。期間入力は「2つの入力欄で範囲の開始と終了を指定するパターン」［H］`patterns/multiple-inputs-field.mdx.txt:48-66`。10 週という幅は［判断］（2 か月強先まで見え、モバイルでも縦に収まる量） |
| **O2** 書く人や時期の偏りを減らす | ① 書く人ごとの公開済み・予定の本数を**並べて比べられる**ようにする ② 予定の無い人を上に出す ③ 時期の偏りは O1 の週ごとの本数で見せる | V3 書く人：テーブル（名前・役割・公開済み・これからの予定・最後に公開した日・次の公開予定日）。**これからの予定が少ない順**に並べ、0 本の人は「予定なし」と書く。名前から V1（その人で絞り込み）へ。V1 の週ごとの「n 本」で、ある週に集中していることも分かる | 「オブジェクト同士を属性情報で比較するユースケースがある場合に有効」［H］`patterns/page-layout.mdx.txt:181`。並び順は［判断］ |
| **O3** 書く人が自分の担当と予定日を忘れない | ① 書く人が**最初の画面で**自分の急ぐ投稿に気づける ② 自分の担当だけを**急ぐ順**に見る場所を用意する ③ 予定日に「あと n 日」「n 日過ぎています」を文字で添える | V1 の見出し領域：ログイン中で、自分の投稿に予定日超過か 14 日以内の予定があれば、1 行の案内（件数と「自分の担当を見る」リンク）。V2 自分の担当：予定日を過ぎた → これから（予定日順）→ 日付未定 → 公開済み、の 4 つの見出しで分ける。各投稿に予定日までの日数。Slack ログイン時に「Slack に予定日の前日通知を送ります（デモ）」と通知を出す | 14 日という幅は［判断］。日数は可変値なので StatusLabel に入れず文字で出す：「インスタンスごとに異なる値をラベルに埋め込まない」［H］`components/StatusLabel.md`（使い方チェックリスト）。Slack 通知は「デモでは通知を出すだけでよい」［B］ |
| **O4** 取りまとめ役が抜けや遅れに早く気づける | ① 遅れ（予定日を過ぎて公開も取りやめもされていない）と抜け（予定の無い週）を**最初の画面の最上部**にまとめる ② 一覧の中でも、遅れている投稿の行に理由を文字で出す | V1 の見出し領域に InformationPanel（警告）「確認が必要なこと」：予定日を過ぎた投稿（タイトルへのリンク付き）と、予定の無い週の一覧。週の中では、遅れた投稿に警告アイコンと「予定日を n 日過ぎています」。V4 投稿でも予定日の近くに同じ表示 | 「重要な情報は、上部や左側に配置する」「優先度が高い情報は、上部に配置する」［H］`patterns/visual-guidance.mdx.txt:50-51`。見出し領域に InformationPanel を置く例［H］`patterns/page-layout.mdx.txt:239`。遅れを 2 つ目の StatusLabel にしない：「1つのオブジェクトに複数のStatusLabelを設定しない」［H］`components/StatusLabel.md`（使い方チェックリスト） |

## 目標以外で先に決めたこと

| 項目 | 決めたこと | 根拠 |
| --- | --- | --- |
| 主ボタン | **一覧の画面（V1・V2・V3）と詳細（V4）には Primary を置かない**。「投稿を追加」「編集」「公開済みにする」は Secondary。Primary はダイアログの完了ボタン（保存する・公開済みにする）だけ。削除ダイアログの完了は Danger | 「［オブジェクトを追加］は一覧画面における主要なアクションにはなりえない」［H］`patterns/visual-guidance.mdx.txt:209`。テーブル操作エリアは Secondary［H］`patterns/smarthr-table.mdx.txt:338`。「1 つの画面で Primary ボタンは最大 1 つまで」「注目を集めることだけを目的に Primary ボタンを使用しない」［H］`components/Button.md:132-134`。ダイアログの完了は Primary、危険な完了は Danger［H］`patterns/modal-ui.mdx.txt:135-136` |
| 入力の形 | 追加・編集は FormDialog（モーダル）。公開済みにするも FormDialog | 「オブジェクトの追加・編集」はモードを検討する場面［H］`patterns/modal-ui.mdx.txt:31` |
| 入力部品 | タイトル：Input／カテゴリ（4 択）：RadioButton／書く人（10 人から複数）：MultiCombobox／公開予定日：Input[type=date]／ステータス（5 択）：RadioButton／記事 URL：Input[type=url]／メモ：Textarea | 選択肢の数と複数可否で選ぶ表［H］`patterns/selection-component-usage.mdx.txt:23-31`。DatePicker は非推奨で Input[type=date]［H］`components/DatePicker.md` |
| 書く人の初期値 | 追加のとき、ログイン中の自分を入れておく | 一般メンバーは自分が入っている投稿しか編集できないため［B］。自分を外すと保存後に編集できなくなる［判断］ |
| 取りやめ | ステータスの変更として扱い、**確認ダイアログを出さない**。取りやめ後も元のステータスに戻せる | 「破壊的な操作であっても、操作後に元に戻せる場合は、処理前の確認は必要ありません」［H］`patterns/delete-dialog.mdx.txt:12` |
| 削除 | 削除ダイアログ（ActionDialog、タイトル「投稿の削除」、本文「この投稿を削除しますか？　この操作は元に戻せません。」、削除対象のタイトル、Danger の「削除」と「キャンセル」） | ［H］`patterns/delete-dialog.mdx.txt:73-131` |
| 権限 | 権限の無い操作のボタンは**出さず、理由を近くに書く**（表示パターン B）。未ログイン：「ログインすると、投稿の追加と、自分が書く投稿の編集ができます。」＋「Slack でログイン」。一般メンバーで他人の投稿：「この投稿は、書く人と編集担当だけが編集できます。」 | ［H］`patterns/access-control-pattern.mdx.txt:13-14, 41-47` |
| 空・失敗・読み込み | 読み込み中は対象領域に Loader。読み込みの失敗は対象領域に NotificationBar（error）と「再読み込み」。データが無いときは「投稿はありません。」と追加ボタン。絞り込み結果が無いときは「該当する投稿はありません。別の条件を試してください。」 | ［H］`patterns/feedback.mdx.txt:510, 564`、`patterns/smarthr-table.mdx.txt:1209, 1250` |
| 保存・削除の成否 | 成功：ダイアログが閉じ画面が変わるため、ページ上部に NotificationBar（success, bold）。失敗：ダイアログを閉じず、ダイアログの `responseStatus` で error を出す | ［H］`patterns/feedback.mdx.txt:115, 221, 238` |
| 状態を URL で開く | `?as=guest|member|editor`（誰として見るか）、`?state=loading|error|empty`、`?dialog=add|edit|publish|delete`、`?result=saved|save-error|deleted|delete-error|published` | 撮影と検査のため［B］「状態を URL のクエリ等で直接開けるように」（作業指示） |
