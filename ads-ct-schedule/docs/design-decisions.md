# ADS 版のデザイン判断

原本（DADS 版）の判断は [digital-go-design-system `docs/design-decisions.md`](https://github.com/takumibv/digital-go-design-system/blob/codex/ct-schedule-ui/docs/design-decisions.md) にあります。ここでは ADS で作り直したときに、何を引き継いで何を変えたか、その理由を記録します。

## 基本方針

この検証の目的は「ADS でどこまで再現できるか」を測ることです。そのため、次の 2 つを決めました。

1. **中身は原本と同じにする。** 画面構成、読む順序、状態（16 種類）、文言、固定データは変えていません。違いが出たら、それはデザインシステムの違いだと言えるようにするためです。
2. **見た目は ADS の標準に任せ、寄せるための上書きをしない。** 自前の CSS は 0 行です。色・余白・角丸はすべて ADS のトークンで指定しました。原本に似せようとして独自のスタイルを足すと、「ADS で再現できた」のか「CSS で無理やり寄せた」のかが分からなくなるからです。

結果として、原本の意図（何を主役にするか、どの順に読ませるか）は引き継ぎ、表現（文字の大きさ、色の強さ、余白の広さ）は ADS らしさに置き換わっています。

## 利用者と主役

原本と同じく、主な利用者は「月曜の CT 直前に相手を確認するメンバー」と考えました。いちばん知りたいのは「今週の自分の相手は誰で、どこで話せばよいか」です。

- **「今週のあなたの CT」を主役にした。** 原本は濃い青の上ボーダーと大きな文字で強調していました。ADS ではこの太い線を表すトークンがないため、薄い青の背景（`color.background.accent.blue.subtlest`）で面として目立たせました。
- 2 人のアバターを最大サイズ（xlarge）にして中央に並べ、その下にハドルを始めるボタンを置きました。「誰と」→「どこで」の順に目が動くようにしています。
- **画面内の主ボタン（primary）は 1 つだけ**にしました。それがこの「Slack でハドルを始める」です。みんなの組み合わせ一覧にあるハドルボタンは default にして、主役と競合しないようにしました。

## 画面ごとの判断

### CT組み合わせ表

- **レイアウト**：PC は「本文＋右の補足欄（320px）」の 2 カラム、モバイルは同じ順序で縦に積みます。原本と同じです。
- **週の移動**：前後の矢印は `IconButton`、真ん中に「今週」ボタンを置きました。今週を表示しているときは「前の週」と「今週」を押せなくして、今どこにいるかが分かるようにしています。
- **みんなの組み合わせ**：1 ペアを 1 行にして、自分のペアの行だけ選択色（`color.background.selected`）を付けました。表の中で自分の位置がすぐ見つかるようにするためです。「あなた」は文字のラベル（Lozenge）でも示し、色だけに頼らないようにしています。
- **この先の CT**：原本は 3 枚のカードを横に並べていました。ADS 版では縦のリストにし、行全体を押せるようにしました。ADS の一覧は行単位のリストが基本で、モバイルでも同じ形のまま使えるからです。祝日の週は警告色のラベル「祝日のためお休み」を付けて、通常の週と区別しています。
- **補足欄**：「参加する人数」と「CT の過ごし方」をそれぞれ枠付きのカードにしました。人数は大きな数字で見せ、本文より一段下がった情報であることを枠で区切って示しています。

### メンバー一覧

- 上部に「参加する／参加しない」の人数カードを並べ、全体の状況を先に伝えます。
- 一覧には ADS 標準の `DynamicTable` を使いました。列（社員番号・メンバー・参加状況・操作）を揃えて読み比べやすくするためです。
- 「設定」「削除」は目立たないボタン（subtle）にしました。一覧を見る人の大半は確認が目的で、削除はまれな操作だからです。
- 削除の確認は小さいモーダルにしました。タイトルに危険を示すアイコンを付け、実行ボタンは赤（danger）にしています。**最初のフォーカスは「キャンセル」**に置き、うっかり Enter を押しても削除されないようにしました。

### 自分の設定・初回設定

- 各項目は「ラベル → 入力欄 → 補足文」の順で、ADS のフォームの型に合わせました。
- エラーは 2 段構えにしました。上部の `SectionMessage` で「何を直せばよいか」をまとめ、各項目の下にも個別のエラー文を出します。原本は上部のまとめだけでしたが、ADS では項目ごとに `ErrorMessage` を出すのが標準なので、それに従いました。
- 保存ボタンは primary、キャンセルは subtle にして、次に押すべきボタンをはっきりさせています。

## 通知の使い分け

原本はすべての通知を画面内のメッセージ（Notice）で出していました。ADS 版では、通知の性質に応じて 2 つに分けました。

| 種類 | ADS の部品 | 例 | 理由 |
| --- | --- | --- | --- |
| 状態が続くもの | `SectionMessage`（その場に残る） | ログイン失敗、保存失敗、入力エラー、未ログインの案内、不参加中 | ユーザーが対応するまで見えている必要がある |
| 操作の結果を一時的に知らせるもの | `Flag`（画面の隅に出る） | 保存しました、削除しました、ハドルのデモ通知 | 作業の流れを止めずに伝えたい。ADS 製品でも同じ使い方をしている |

## ラベル（Lozenge）の色の意味

色の意味を画面全体で揃えました。どのラベルも文字で意味が読めるので、色が分からなくても困りません。

| 色（appearance） | 使った場所 | 意味 |
| --- | --- | --- |
| 青（information） | 今週、あなた | 自分や現在に関係する情報 |
| 緑（success） | 参加する | 良い状態 |
| 灰（default） | 参加しない、来週、14:00 開始 | 中立の情報 |
| 黄（warning） | 祝日のためお休み、初回設定が未完了 | 注意してほしいこと |

## アクセシビリティ

- 「本文へ移動」のスキップリンクを置き、キーボードで操作したときだけ表示されるようにしました。
- ADS のレイアウト部品（`Stack` など）は `section` や `aside` になれないので、外側を本来の HTML 要素で包み、ページの構造が支援技術に伝わるようにしました。
- 見出しは h1 → h2 → h3 の順に並べ、見た目の大きさと見出しのレベルを分けて指定しています。
- アイコンだけのボタンには「前の週」のようにラベルを付けました。
- axe（WCAG 2.1 AA）の検査では、16 状態 × 2 幅のすべてで違反は 0 件でした。

## 再現できなかったこと（妥協点）

| 原本の意図 | ADS 版でどうなったか | 理由 |
| --- | --- | --- |
| 色付きのイニシャルで人を見分ける | 全員が同じ人型アイコンになった | ADS の Avatar は画像がないとイニシャルを出せない |
| ゆったりした余白と大きな文字（本文 16px、見出し 32px） | 本文 14px が基本で、全体に詰まった印象 | ADS は業務アプリ向けに情報密度を優先しているため |
| 濃い青の強いアクセント | 薄い青の背景で代用 | 太い線や濃い青の面を表すトークンがない |
| Noto Sans JP で統一 | 和文は OS 標準のフォントになる | ADS は欧文のシステムフォントだけを指定している |
| ブランドバー＋サービスバーのヘッダー | ADS のレイアウト部品で自作 | ADS のナビゲーション部品は Atlassian 製品専用の作りで、この用途には重すぎる |

## まとめ

**「何を主役にし、どの順に読ませるか」という設計の意図は ADS でもそのまま実現できました。** 一方で、DADS が持っていた「読みやすさ・やさしさ」の表現（大きな文字、広い余白、色で見分ける人）は ADS の標準からは出てきません。ADS 版は「チームの業務ツール」らしい、引き締まった見た目になります。どちらを選ぶかは、この画面を「気軽に開くお知らせ」と見るか、「業務の道具」と見るかで決まると考えます。
