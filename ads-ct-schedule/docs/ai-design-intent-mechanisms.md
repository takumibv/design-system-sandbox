# デザイン意図を AI 実装に届ける仕組み：ADS と DADS の比較

Atlassian Design System（ADS）とデジタル庁デザインシステム（DADS）について、AI が実装するときに「そのデザインシステムらしさ」（部品の使い分け、トーン、禁止事項）が伝わるようにする工夫を調べました。公開されているパッケージ、リポジトリ、サイトを実際に読んでいます（2026-11-01 時点）。

## 結論

| | ADS | DADS |
| --- | --- | --- |
| 誰に向けた AI 対応か | **デザインシステムを使ってアプリを作る人**（の AI） | **デザインシステムのサンプル実装を作る人**（の AI） |
| 意図の置き場所 | 構造化データ（部品ごとの使い方・文言・アクセシビリティの指針）。そこから llms.txt、MCP、CLI、スキルに配る | Web サイトの文章（概要・使い方・アクセシビリティ）。リポジトリには AGENTS.md と実装規約のスキル |
| AI が読める形で配っているか | ◎ llms.txt 8 種、ホスト型 MCP、CLI | △ サイトは HTML のみ（llms.txt なし）。リポジトリの Markdown は読める |
| 機械で強制しているか | ◎ ESLint 117 ルール＋型でトークン以外を拒否 | △ 規約は文章（スキル）で書かれ、強制は汎用の lint（Biome、Markuplint）のみ |

**ADS は「意図をデータとして持ち、配り、lint で強制する」仕組みが一通りそろっています。DADS は意図を人が読む文章として丁寧に書いていますが、AI 向けの配布経路はまだありません。** DADS の AI 対応は、サンプル実装を作るコントリビューター向けに限られています。

---

## ADS：意図を「データ → 配布 → 強制」の 3 段で届ける

### 1. 意図をデータとして持つ

`@atlaskit/ads-mcp` に入っている部品カタログ（`components.codegen.js`、150 部品）には、各部品に次の項目があります。

| 項目 | 持っている部品の数 | 中身 |
| --- | --- | --- |
| `usageGuidelines` | 144 | いつ使い、いつ使わないか。他の部品との使い分け |
| `contentGuidelines` | 107 | 文言の書き方 |
| `accessibilityGuidelines` | 70 | フォーカス順、見出しレベルなど |
| `keywords`、`category`、`status`、`examples` | 150 | 検索用の語、分類、成熟度、実例コード |

今回使った部品の実際のデータを抜粋します。

- **Button**：「主ボタン（primary）は 1 セクションに 1 つまで」「補助的な操作には subtle」「danger は控えめに」「操作にはボタン、遷移にはリンク」
- **SectionMessage**：「対応や解決まで残り続ける、セクション単位の重要な情報に使う」「サイト全体なら Banner、出来事の後なら Flag」
- **Flag**：「確認や通知に使う。左下に出る」「重要なメッセージは自動で消さない」
- **Lozenge**：「状態・優先度など意味のある属性に使う」「色は必ず短いラベルと組み合わせる」
- **Modal**：「侵襲的なので控えめに使う」「1 モーダル 1 タスク」「フッターでは主ボタンを副ボタンの右に置く」

トークンにも説明が付いています。たとえば `color.background.selected` には「選択状態を伝える要素の背景に使う。選択はキーボードフォーカスやホバーとは別物」とあります。

文言のトーンも別ファイル（`llms-content.txt`）にまとまっています。内容は、ボイス＆トーン、メッセージの種類ごとの書き方、インクルーシブな言葉選び、日付の書式などです。

### 2. 同じデータを複数の経路で配る

README には「CLI は MCP の薄い層で、独自のデータを持たない。正となる情報源は 1 つ」と書かれています。

| 経路 | 内容 | 想定する使い方 |
| --- | --- | --- |
| **llms.txt 群** | `atlassian.design/llms.txt` を入口に、components（489KB）、tokens、primitives、styling、a11y、content、full（588KB）の 8 種 | AI に URL を渡して読ませる |
| **MCP サーバー** | `https://mcp.atlassian.com/v1/ads/public/mcp`（ホスト型）または `npx @atlaskit/ads-mcp`。`ads_search_components`、`ads_plan`（部品・トークン・アイコンをまとめて引く）、`ads_analyze_a11y` など | エディターの AI が必要なときに検索する |
| **CLI** | `npx @atlaskit/ads-cli`。MCP と同じ処理をターミナルから呼ぶ | MCP の設定なしで AI に使わせる |
| **スキル** | `atlassian-design-system`、`ui-styling-standard`、`a11y-foundation` | 作業の手順ごと AI に渡す |
| **AGENTS.md** | `ads-cli init` がリポジトリの AGENTS.md に案内を追記する | 「UI を作る前に ADS を参照せよ」と AI に最初に伝える |

MCP サーバー自体にも AI への指示文が入っています。「ADS の部品を優先し、ADS にないときだけ他の `@atlaskit` パッケージを調べる」「アクセシビリティの専門家としてふるまう」といった内容です。

ただしスキル本体（`@atlassian/skills`）は npm に公開されておらず（404）、Atlassian 社内向けです。社外で `init` を実行すると、スキルは入らず、公開ガイダンスへの案内だけが AGENTS.md に書かれます。

### 3. lint と型で強制する

- **ESLint プラグイン 2 種**：`@atlaskit/eslint-plugin-design-system`（117 ルール）と `@atlaskit/eslint-plugin-ui-styling-standard`。
  - 警告文が**AI への作業指示として書かれている**のが特徴です。例：「Lozenge appearance="moved" を "warning" に置き換え、自動修正を適用せよ」「href、遷移の挙動、リンク文言は保ったまま」。
  - 素の HTML（`<button>`、`<img>`、`<a>`）の使用、プレースホルダー、見出しレベルの指定漏れなども検出します。
- **型**：`xcss` はトークン以外の色や余白を型エラーにします。レイアウト部品の `as` に指定できる要素も絞られています。
- **移行ガイドと codemod**：古い API を新しい API に機械的に書き換える手順が、MCP や CLI からも引けます。

## DADS：意図を「人が読む文章」として丁寧に書く

### 1. 意図はサイトの文章にある

`design.digital.go.jp` の各部品には、概要・**使い方**・アクセシビリティ・変更履歴のページがあります。使い方の解説は ADS より深く、判断の理由まで書かれています。

ボタンの「使い方」ページの例：

- 塗りボタンはプライマリー（重要度：高）、アウトラインはセカンダリー（中）、テキストはターシャリー（低）
- **プライマリーは 1 画面に原則 1 つ。セカンダリーは文脈ごとに原則 3 つまで。** 4 つ以上になるならフロー自体を見直す
- ターシャリーはキャンセルなど、フローを中断する操作に使う
- 進む操作は右、戻る・キャンセルは左に置く。モバイルで縦に積むときの順序
- 「ヘッダーのログインボタンよりフローを進めるボタンの方が重要」といった、画面の中の役割で重要度を決める考え方

ただし、これらは HTML の Web ページとしてだけ提供されています。

- `llms.txt` はありません（404）。
- MCP サーバーや CLI もありません。
- デザイントークン（`@digital-go-jp/design-tokens` の `tokens.json`）は値だけを持ち、説明文は 0 件です。意図はトークン名に込められています。たとえば `text-std-16N-170` は「標準・16px・Normal・行間 170%」を表します。

### 2. リポジトリの AI 対応はサンプル実装を作る側向け

公式のサンプル実装リポジトリ（HTML 版、React 版）には AGENTS.md と `.agents/skills/` があります。

| リポジトリ | AI 向けファイル | 主な内容 |
| --- | --- | --- |
| React 版 | AGENTS.md ＋ スキル 7 個 | **component-rules**（Tailwind の標準色・標準サイズの禁止、トークン必須、`data-*` で状態を表す、部品本体に state や effect を置かない、部品同士を依存させない）、port-html-to-react（HTML 版からの移植）、write-component-docs、write-tests、review、pre-completion-check、create-commit |
| HTML 版 | AGENTS.md ＋ スキル 2 個 | develop-component、write-document（ドキュメントは素の Markdown で書く） |

ほかに次のものがあります。

- **部品の仕様書（`component-spec.md`、React 版の 11 部品）**：HTML 版からの移植計画を日本語で書いたもの。公開する構成要素、props、初期フォーカスの扱い、API に入れないものまで書かれている。
- **開発方針（`development-policy.mdx`）**：設計思想（カスタマイズ性、シンプルさ、HTML/CSS ネイティブ優先）、JIS X 8341-3 と WCAG 2.2 AA、強制カラーモードや視覚効果低減モードへの配慮。

これらはすべて「DADS のサンプル部品を正しく作る」ためのものです。**「DADS を使ってアプリ画面を作る AI」に、ボタンの使い分けのような使い方の意図を届ける仕組みは、今のところありません。** 利用者は部品のコードをコピーして使う前提で、意図はコードとサイトの文章から読み取ることになります。

### 3. 強制は汎用の lint のみ

Biome と Markuplint（見出しレベルの飛びなど HTML の妥当性を検査）は使われています。一方で「プライマリーは 1 つ」「標準の Tailwind 色を使わない」といった DADS 固有のルールは、スキルの文章に書かれているだけで、機械では検査されていません。

## 今回の検証で実際にどう効いたか

### ADS 版（今回の作業）

- 使ったのは CLI だけでした。CLI v0.11.1 の `component` コマンドは props と実例は出しますが、**使い方の指針は表示しませんでした**（データ自体は MCP 側にあります）。トークンの `token` コマンドは指針を表示しました。
- そのため、ADS らしさの判断は主に次の 4 つから来ています。
  1. CLI の検索結果と props
  2. 型エラー（`xcss` や `as` の制約）
  3. 作った後の ESLint の警告（18 件 → 6 件）
  4. もともと持っていた ADS の知識
- `llms.txt` には「`@atlaskit/primitives`（emotion 版）は legacy、`/compiled` を推奨」と最初から書かれていました。**最初に llms.txt か MCP を読んでいれば、`no-emotion-primitives` の警告は避けられました。**
- 後から MCP の指針と照らし合わせると、多くの判断は一致していました。主ボタンを 1 つにする、成功通知は Flag、続く状態は SectionMessage、モーダルの主ボタンを右に置く、Lozenge を色＋文字で使う、などです。
- 一方でずれもありました。削除確認モーダルで最初のフォーカスを「キャンセル」に置いたのは安全側に倒した判断です。ADS の指針は「閉じるボタン（またはタイトル）が最初」としています。

### 原本（DADS 版）

原本のリポジトリでは、DADS の公式部品に加えて、**利用者側（このプロジェクト）が意図を文章で補っていました。**

- `docs/requirements-original.md`：要件
- `docs/design-decisions.md`：誰のための画面か、何を主役にするか、色・文字・余白の方針
- `docs/ui-review-harness.md`：状態と Story の対応、レビューでの指摘の書き方

ハドルボタンを 1 画面で塗りボタン 1 つに絞っていたのは、DADS の「プライマリーは 1 画面に原則 1 つ」と一致しています。ただしこれは、AI が DADS のサイトを読んで得た情報ではありません。

## 示唆：AI に意図を届けるには 3 つの層が要る

| 層 | 例 | ADS | DADS | 誰が書くか |
| --- | --- | --- | --- | --- |
| ① 部品の使い分け | 主ボタンは 1 つ、通知の種類ごとの部品 | ◎ データ＋配布＋lint | ○ 文章はあるが AI に届かない | デザインシステム |
| ② プロダクトのトーン | 文言の調子、余白の広さ、色の強さ | ○ content standards（Atlassian 製品のトーン） | △ サイトの「ガイダンス」 | デザインシステム＋プロダクト |
| ③ 画面の意図 | この画面で何を主役にするか | × | × | **プロジェクト**（design-decisions.md など） |

どちらのデザインシステムも ③ は持っておらず、プロジェクト側で書く必要があります。今回の原本にあった `design-decisions.md` がまさにこの役割です。いわゆる DESIGN.md のようなファイルは、どちらのデザインシステムも配布していません。ADS では llms.txt とスキル、DADS では AGENTS.md（実装規約）とサイト（意図）が、その役割を分担しています。

### DADS で AI 実装の精度を上げるなら（このプロジェクトでできること）

1. **サイトの「使い方」を Markdown のスキルにまとめる。** ボタンの重要度と配置、通知の使い分けなどを、利用者リポジトリの `.agents/skills/` か AGENTS.md に置く。これで①を自前で補える。
2. **トークンの使い分けを文章で補う。** たとえば「`blue-900` は主操作、`blue-50` は選択中の背景」のように、トークンに説明が付いていない部分を表にする。
3. **ルールを lint にする。** 「Tailwind の標準色を使わない」「トークン以外の値を使わない」は、原本の `ui-review-harness.md` の「次に追加する候補 3」とも一致する。Biome のカスタムルールか ESLint で検出する。
4. **プロジェクトの `design-decisions.md` を AGENTS.md から参照させる。** これで③を毎回 AI に読ませられる。
5. ADS 方式の 3 段（データ → 配布 → 強制）に倣い、まずは 1 と 4 から始める。llms.txt や MCP を自作するのは、効果を確かめてからでよい。
